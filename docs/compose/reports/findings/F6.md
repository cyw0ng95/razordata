# F6: SQLite vs PostgreSQL query planner architecture and Razordata adoption opportunities

## Findings

### [1] SQLite's N3 (N Nearest Neighbors) algorithm is O(K*N) time, keeping N best partial plans at each step of join ordering — directly analogous to Razordata's current N3 implementation
- quote: "With N3, instead of choosing just one nearest neighbor for each step, the algorithm keeps track of the N best paths at each step for some small integer N... the storage requirement is O(N) and the computation time is O(K*N)"
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12 (last updated)
- confidence: high

### [2] SQLite's N3 default N values are tuned per join-size: N=1 for simple queries, N=5 for two-way joins, N=10-18 for 3+ table joins (star-query aware) — Razordata uses n3HeapMaxSize=24 as a flat constant
- quote: "The initial implementation of NGQP chooses N=1 for simple queries, N=5 for two-way joins and N=10 for all joins with three or more tables. Later, the N value for joins with three or more tables was raised to 12 or to 18 if the join is against a star-schema."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [3] SQLite 3.49.0 star-query heuristic raises full-table scan cost of dimension tables to prevent greedy N3 from prematurely discarding the fact-table search path — Razordata has bushy join detection but no equivalent cost adjustment
- quote: "The current heuristic, as of version 3.49.0 (2025-02-06), is to artificially raise the estimated full-table scan cost for dimension tables so that the cost is slightly greater than the cost of finding the relevant rows of the fact table."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [4] PostgreSQL uses dynamic programming for ≤12 tables and GEQO (genetic algorithm) for >12 tables — Razordata has single-start N3 for >8 tables, with a documented future REQ (REQ001109) for GEQO
- quote: "The planner will rewrite explicit JOIN constructs into lists of FROM items whenever a list of no more than this many items would result... Setting this value to geqo_threshold or more may trigger use of the GEQO planner"
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-11-14 (PostgreSQL 17)
- confidence: high

### [5] PostgreSQL collects three types of extended statistics (functional dependencies, multivariate NDV, multivariate MCV lists) via CREATE STATISTICS — Razordata has single-column NDV and per-column MCV lists but no cross-column correlation statistics
- quote: "It is common to see slow queries running bad execution plans because multiple columns used in the query clauses are correlated. The planner normally assumes that multiple conditions are independent of each other... PostgreSQL has the ability to compute multivariate statistics, which can capture such information."
- url: https://www.postgresql.org/docs/17/planner-stats.html
- source_type: primary
- published: 2024-11-14
- confidence: high

### [6] PostgreSQL's default_statistics_target (100) controls histogram/MCV sample depth per column, configurable via ALTER TABLE SET STATISTICS — Razordata's ANALYZE uses a fixed reservoir sample size of 10,000 across all columns
- quote: "The default limit is presently 100 entries. Raising the limit might allow more accurate planner estimates to be made, particularly for columns with irregular data distributions"
- url: https://www.postgresql.org/docs/17/planner-stats.html
- source_type: primary
- published: 2024-11-14
- confidence: high

### [7] PostgreSQL's enable_memoize (introduced PG14) caches inner-side results of parameterized nested-loop joins to avoid redundant inner-side scans — Razordata has no equivalent memoize node for parameterized NLJ
- quote: "Enables or disables the query planner's use of memoize plans for caching results from parameterized scans inside nested-loop joins. This plan type allows scans to the underlying plans to be skipped when the results for the current parameters are already in the cache."
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-11-14
- confidence: high

### [8] PostgreSQL's cost model is fully user-tunable via GUCs (seq_page_cost=1.0, random_page_cost=4.0, cpu_tuple_cost=0.01, etc.) — Razordata has both a legacy heuristic model and a PostgreSQL-compatible CostParams struct, but the parametric model lacks effective_cache_size and parallel cost parameters
- quote: "Only their relative values matter, hence scaling them all up or down by the same factor will result in no change in the planner's choices... Unfortunately, there is no well-defined method for determining ideal values for the cost variables."
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-11-14
- confidence: high

### [9] SQLite stores ANALYZE results in sqlite_stat1 (per-index row counts), sqlite_stat3 (leftmost-column histogram), and sqlite_stat4 (all-column histograms) — Razordata persists stats to razor_stat1 system table and catalog blobs, but only stores equi-depth histograms without multi-column coverage
- quote: "The SQLITE_ENABLE_STAT3 and SQLITE_ENABLE_STAT4 options causes the ANALYZE command to collect a histogram of column content in the sqlite_stat3 or sqlite_stat4 tables and to use this histogram to make a better guess at the best query to use for range constraints"
- url: https://www.sqlite.org/optoverview.html
- source_type: primary
- published: 2026-03-22
- confidence: high

### [10] Razordata's xxhash64 plan memoization (not SHA-256 as design docs claim) with parameterized normalization is architecturally similar to PostgreSQL's plan_cache_mode (auto/custom/generic) but simpler — PG also supports prepared statement plan reuse across executions
- quote (Razordata code): "TestSerializeKey_NotSHA256Length verifies the key is the 16-hex-character xxhash digest, not the 64-hex-character SHA-256 digest. REQ000584."
- url: (internal codebase — /workspace/internal/SQF/PL/memo.go)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [11] SQLite's ANALYZE auto-triggered by PRAGMA optimize keeps stats fresh without manual intervention — Razordata requires explicit ANALYZE with no automatic background refresh
- quote: "The current recommendation for avoiding problems such as this one is to simply run 'PRAGMA optimize' just prior to closing each database connection... Because of this, query planning issues such as the one described here no longer come up."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [12] Razordata's learned selectivity component (blending histogram-based and online-learned predictions) has no equivalent in either SQLite or PostgreSQL — this is a novel approach that could be a differentiator
- quote (Razordata code, predicate.go:240-259): "lm := pl.Learned(); if lm.IsTrained() { features := lm.PredicateFeatures(...); learnedSel := lm.Predict(features); // blended with histogram selectivity via alpha weighting }"
- url: (internal codebase — /workspace/internal/SQB/EX/predicate.go)
- source_type: primary
- published: 2026-07-09
- confidence: high
