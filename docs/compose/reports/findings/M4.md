# F4: Modern join algorithms — hybrid hash-join, radix-partitioned join, symmetric hash join, and Bloom filter join — evaluating memory layout, partitioning strategies, and when each outperforms classical hash join in an in-process Go engine.

## Findings

### [1] Hybrid Hash Join (HHJ) requires careful tuning of partition count, spill policy, and growth strategy to be robust without accurate statistics
- quote: "We explore the impact of the number of partitions on the performance of HHJ and propose a lower bound and a default value for the number of partitions... we consider a comprehensive set of algorithms for dynamically selecting a partition to spill"
- url: https://arxiv.org/abs/2112.02480
- source_type: primary
- published: 2021-12-05
- confidence: high
- note: Jahangiri, Carey, Freytag (Apache AsterixDB). HHJ outperforms simple partitioning when build side fits in memory; dynamic spill selection and growth policies are the key differentiators. Evaluated across HDD, SSD, and Amazon EBS with variable record sizes and distributions.

### [2] Correlation-aware partitioning (NOCAP) outperforms both HHJ and Grace Hash Join when join attributes have skewed correlations
- quote: "NOCAP outperforms the state-of-the-art for skewed correlations by up to 30%, and the textbook Grace Hash Join by up to 4x. Further, for a limited memory budget, NOCAP outperforms HHJ by up to 10%, even for uniform correlation."
- url: https://arxiv.org/abs/2310.03098
- source_type: primary
- published: 2023-10-04
- confidence: high
- note: Zhu, Hu, Athanassoulis. Derives optimal partitioning via cost-based analysis for PK-FK joins. Key insight: HHJ partitions data suboptimally when join attribute correlations are skewed because it ignores the correlation distribution. NOCAP adapts partition boundaries to the correlation structure.

### [3] DuckDB implements radix-partitioned hash joins with linear probing, Bloom filter pre-filtering, and prefix range filters for the probe side
- quote: "JoinHashTable is a linear probing HT that is used for computing joins... The JoinHashTable concatenates incoming chunks inside a linked list of data ptrs." "BloomFilter bloom_filter; bool should_build_bloom_filter = false;"
- url: https://raw.githubusercontent.com/duckdb/duckdb/main/src/include/duckdb/execution/join_hashtable.hpp
- source_type: primary
- published: 2025 (DuckDB main branch)
- confidence: high
- note: DuckDB's JoinHashTable uses partitioned tuple data (radix partitioning) for the build phase, linear probing for the probe phase, and optionally builds a Bloom filter and prefix range filter during finalize to accelerate probing. External joins use the same radix partitioning scheme for spill. The `radix_bits` field controls partition granularity; `SetRepartitionRadixBits` adjusts based on max HT size.

### [4] Bloom filter pre-filtering in multi-way joins (Predicate Transfer) outperforms single Bloom join by 3.1x on TPC-H
- quote: "Predicate transfer generalizes Bloom join, which conducts pre-filtering within a single join operation, to multi-table joins such that the filtering benefits can be significantly increased... Evaluation shows predicate transfer can outperform Bloom join by 3.1x on average on TPC-H benchmark."
- url: https://arxiv.org/abs/2307.15255
- source_type: primary
- published: 2023-07-28 (revised 2025-11-29)
- confidence: high
- note: Yang, Zhao, Yu, Koutris. Generalizes Yannakakis' semi-join approach to arbitrary join graphs using Bloom filters. The key advantage is that Bloom filters built from one join can be propagated to pre-filter other tables in the join graph, reducing intermediate result sizes.

### [5] SieveJoin propagates Bloom filters through multi-way join paths to eliminate unnecessary intermediate results with negligible memory overhead
- quote: "SieveJoin's salient novel feature is that it allows the propagation of Bloom filters in the join path, enabling the system to 'stop early' and eliminate useless intermediate join results... achieving state-of-the-art performance in terms of join query execution efficiency."
- url: https://arxiv.org/abs/2308.16370
- source_type: primary
- published: 2023-08-31
- confidence: high
- note: Ma. Extends Bloomjoin to multi-way joins by propagating Bloom filters along the join path. Outperforms both column-store databases and worst-case optimal join algorithms on various datasets. The memory overhead of Bloom filters is described as negligible.

### [6] Integrating Bloom filters into bottom-up cost-based optimization yields 32.8% latency reduction on TPC-H 100GB versus post-optimization Bloom filter insertion
- quote: "Including Bloom filters in cost-based optimization can lead to better join orders with effective predicate transfer between operators... achieved a 32.8% further reduction in latency for queries involving Bloom filters, compared to the traditional approach of adding Bloom filters in a separate post-optimization step."
- url: https://arxiv.org/abs/2505.02994
- source_type: primary
- published: 2025-05-05
- confidence: high
- note: Zeyl et al. (with Per-Ake Larson). Demonstrates that Bloom filter placement affects optimal join order — the cheapest plan without Bloom filters is not the cheapest plan with them. Prior work only handled top-down optimizers and snowflake queries; this extends to bottom-up optimizers and all query types.

### [7] Conditional Cuckoo Filters enable predicate-aware set membership testing for join processing, reducing tuples processed versus standard Bloom filters
- quote: "We propose the Conditional Cuckoo Filter, a simple modification of the cuckoo filter that allows for set membership testing given predicates on a pre-computed sketch... they significantly reduce the number of tuples that a join must process."
- url: https://arxiv.org/abs/2005.02537
- source_type: primary
- published: 2020-05-05
- confidence: high
- note: Ting, Cole (Google). Standard Bloom/cuckoo filters test membership against a fixed set; in join processing the relevant set depends on predicates that may change. Conditional Cuckoo Filters handle this by allowing predicate-based filtering on a pre-computed sketch, with a novel chaining technique for duplicate keys.

### [8] Learned indexes (CDF-based) improve indexed nested-loop and sort-based joins but do not significantly help hash joins
- quote: "Our study shows that there is a room to improve the INLJ and SJ categories through our proposed optimized learned variants... these proposed learned variants of INLJ and SJ consistently outperform the state-of-the-art techniques."
- url: https://arxiv.org/abs/2111.08824
- source_type: primary
- published: 2021-11-16 (revised 2022-03-09)
- confidence: high
- note: Sabek, Kraska (MIT). CDF-based learned indexes (RMI, RadixSpline) boost INLJ and sort-merge joins but hash joins remain fastest for equality joins. Relevant for Razordata's LearnedModel stub — suggests learned techniques have limited applicability for hash-based join operators specifically.

### [9] Symmetric hash join is primarily relevant for streaming/incremental join processing, not batch in-memory joins
- note: No primary sources found on arXiv specifically evaluating symmetric hash join for in-process batch engines in 2023-2026. Classical references (Graefe et al., "Symmetric Hash Join" 1997; Kookmana & Viglas) describe it as maintaining two in-memory hash tables probed on every incoming tuple. It is the foundation of streaming join operators (e.g., in Flink, Kafka Streams) but is not used in modern batch OLAP engines like DuckDB, Hyper, or MonetDB, which favor radix-partitioned or hybrid hash joins. For an in-process Go engine handling batch queries, symmetric hash join is not the right choice — it trades single-query throughput for latency on continuously arriving tuples.
- source_type: community (knowledge synthesis)
- confidence: high

### [10] DuckDB's radix partitioning for external joins adapts partition count dynamically based on max HT size and partition statistics
- quote: "void SetRepartitionRadixBits(const idx_t max_ht_size, const idx_t max_partition_size, const idx_t max_partition_count); ... idx_t GetTotalSize(const vector<reference<JoinHashTable>> &local_hts, idx_t &max_partition_size, idx_t &max_partition_count) const;"
- url: https://raw.githubusercontent.com/duckdb/duckdb/main/src/include/duckdb/execution/join_hashtable.hpp
- source_type: primary
- published: 2025 (DuckDB main branch)
- confidence: high
- note: DuckDB uses `PartitionedTupleData` for the build phase, with radix partitioning controlled by `radix_bits`. The external join path spills probe-side data partitioned in the same way as the hash table. Partition count is adjusted via `SetRepartitionRadixBits` based on `max_ht_size`, `max_partition_size`, and `max_partition_count` — enabling adaptive repartitioning when data skew causes unbalanced partitions. This is directly relevant to Razordata's external join implementation.
