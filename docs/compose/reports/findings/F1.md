# F1: Angle 1 — SQLite Query Optimizer Source Architecture: Source-level analysis of SQLite's join ordering (NGQP/N3 bitmask DP), index selection (sqlite3WhereBegin), statistics (sqlite_stat1 row counts/histograms, sqlite_stat4 column histograms), selectivity estimation (equi-join uniform assumption, sqlite_stat4 range predicates), cost model, and pragmas (ANALYZE, OPTIMIZE). Focus: what SQLite gets right for embedded databases and where it deliberately simplifies.

## Findings

### [1] SQLite's NGQP uses N3 (N-Nearest-Neighbors) for join ordering, replacing the legacy NN (Nearest-Neighbor) heuristic in version 3.8.0 (2013-08-26), with configurable N parameter: N=1 for simple queries, N=5 for 2-way joins, N=10 (raised to 12, then 18 for star-schemas) for 3+ tables, achieving O(K*N) complexity where K=number of tables.
- quote: "With N3, instead of choosing just one nearest neighbor for each step, the algorithm keeps track of the N best paths at each step for some small integer N."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12 (last updated)
- confidence: high

### [2] SQLite finds optimal join order for TPC-H Q8 (8-way join) at N≥10; NN heuristic yields a plan 750x slower than optimal (log-cost 36.92 vs 27.38) because NN only considers single best path at each step and misses globally better combinations.
- quote: "The plan computed using NN is R-N1-N2-S-C-O-L-P with a cost of 36.92. The shortest path... is P-L-O-C-N1-R-S-N2 with a cost of 27.38... the shortest path is nearly 750 times faster."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [3] SQLite implements joins exclusively as nested loops; inner joins are freely reorderable, outer joins are not (commutativity/associativity constraints); CROSS JOIN is treated specially — tables are never reordered, giving developers a mechanism to force specific nesting order.
- quote: "SQLite implements joins as nested loops. The default order of the nested loops in a join is for the left-most table in the FROM clause to form the outer loop and the right-most table to form the inner loop."
- url: https://www.sqlite.org/optoverview.html
- source_type: primary
- published: 2025-05-31
- confidence: high

### [4] Each table in a FROM clause can use at most one index (except OR-clause optimization), and SQLite estimates total work for each candidate index to select the best one; the unary "+" operator disqualifies WHERE clause terms from index usage as a developer override.
- quote: "Each table in the FROM clause of a query can use at most one index (except when the OR-clause optimization comes into play) and SQLite strives to use at least one index on each table."
- url: https://www.sqlite.org/optoverview.html
- source_type: primary
- published: 2025-05-31
- confidence: high

### [5] sqlite_stat1 stores per-index NDV (number of distinct values) cascading statistics: the stat column is a list of K+1 integers for a K-column index — row count, then average rows sharing the same value for first column, first two columns, etc.; also includes optional `sz=NNN` (avg row size) and `unordered` tokens.
- quote: "The first integer in this list is the approximate number of rows in the index. The second integer is the approximate number of rows in the index that have the same value in the first column of the index. The third integer is the number of rows in the index that have the same value for the first two columns."
- url: https://www.sqlite.org/fileformat2.html#stat1tab
- source_type: primary
- published: 2025-05-31
- confidence: high

### [6] sqlite_stat4 (compile-time opt-in via SQLITE_ENABLE_STAT4) stores column histograms with 10-40 samples per index; each sample records nEq, nLt, nDLt as lists of N integers (one per column prefix), enabling range predicate selectivity estimation on the leftmost column; sqlite_stat3 (leftmost column only) is deprecated in favor of stat4.
- quote: "The sqlite_stat4.sample column holds a BLOB in the record format that encodes the indexed columns followed by the rowid... The sqlite_stat4.nEq column holds a list of N integers where the K-th integer is the approximate number of entries in the index whose left-most K columns exactly match the K left-most columns of the sample."
- url: https://www.sqlite.org/fileformat2.html#stat4tab
- source_type: primary
- published: 2025-05-31
- confidence: high

### [7] Without ANALYZE, SQLite uses a default assumption of 10 duplicates per value in the leftmost index column; skip-scan optimization requires approximately 18+ duplicates to be profitable, so it never activates on unanalyzed databases.
- quote: "Without the results of ANALYZE, SQLite has to guess at the 'shape' of the data in the table, and the default guess is that there are an average of 10 duplicates for every value in the left-most column of the index. Skip-scan only becomes profitable when the number of duplicates is about 18 or more."
- url: https://www.sqlite.org/optoverview.html#skipscan
- source_type: primary
- published: 2025-05-31
- confidence: high

### [8] SQLite's cost model is log-additive for nested loops (costs multiply in linear space but are represented logarithmically); it estimates setup cost (automatic index construction), per-step iteration cost, row count, and sorting cost, with the outermost loop using a standalone "*" cost (no dependency on other tables).
- quote: "The costs are comprised of multiple numbers... there is a 'setup' cost that is incurred just once when the query starts... there is the cost of running each step of the loop. Finally, there is an estimate of the number of rows generated by the loop, which is information needed in estimating the costs of inner loops."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [9] The star-query heuristic (circa 2024-2025, version 3.49.0) artificially raises full-table scan costs for dimension tables in star schemas to prevent them from displacing fact-table searches from the N-best set early in the N3 algorithm; this replaced an earlier approach (3.47.0-3.48.0) that lowered fact-table costs, which caused other regressions.
- quote: "The current heuristic, as of version 3.49.0 (2025-02-06), is to artificially raise the estimated full-table scan cost for dimension tables so that the cost is slightly greater than the cost of finding the relevant rows of the fact table."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [10] PRAGMA optimize (introduced 3.18.0, significantly enhanced 3.46.0) selectively runs ANALYZE on tables based on accumulated query-planner usage records within a connection, auto-limits analysis scope for large databases, and is the recommended mechanism over raw ANALYZE; PRAGMA analysis_limit (3.32.0) enables approximate ANALYZE by capping rows scanned per index (100-1000 recommended), but sqlite_stat4 histograms require full scans.
- quote: "The PRAGMA optimize command will automatically run ANALYZE when needed... Since SQLite version 3.46.0 (2024-05-23), the 'PRAGMA optimize' command automatically limits the scope of ANALYZE subcommands so that the overall 'PRAGMA optimize' command completes quickly even on enormous databases."
- url: https://www.sqlite.org/lang_analyze.html
- source_type: primary
- published: 2026-04-21
- confidence: high

### [11] SQLite deliberately simplifies for embedded use: no hash joins in the traditional sense (added only in 3.38.0 as automatic query-time indexes), no sort-merge joins, no parallel query execution, no statistics background worker, no extensible cost model; the Query Planner Stability Guarantee (QPSG, opt-in via SQLITE_ENABLE_QPSG) ensures deterministic plan selection — a key embedded guarantee that client/server databases don't offer.
- quote: "Client/server SQL database engines do not normally make this guarantee... DBAs are not available to fix problems in an embedded database like SQLite, and hence SQLite is careful to ensure that plans do not change unexpectedly after deployment."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [12] Automatic query-time indexes are created when no existing index aids a query and the expected lookup count exceeds log(N); these are transient, statement-scoped, and cost O(N*logN) to build — SQLite defaults to assuming N=1,000,000 rows when ANALYZE data is absent.
- quote: "An automatic index will only be created if SQLite expects that the lookup will be run more than logN times during the course of the SQL statement... In the absence of ANALYZE information, SQLite guesses that N is one million."
- url: https://www.sqlite.org/optoverview.html#autoindex
- source_type: primary
- published: 2025-05-31
- confidence: high
