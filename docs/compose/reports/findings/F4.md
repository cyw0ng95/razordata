# F4: Angle 4 — Selectivity Estimation and Cost Modeling Approaches: Cross-system analysis of selectivity estimation: NDV-based (SQLite/Razordata) vs histogram-based (sqlite_stat4, PostgreSQL histograms) vs MCV-list-based (PostgreSQL pg_statistic). Cover equality, range, equi-join, multi-predicate AND/OR, NULL handling, zero-row problem. Map to academic literature (Selinger 1979, Ioannidis 1992, learned cardinality). Assess achievable accuracy without PostgreSQL's collection overhead for an embedded engine.

## Findings

### [1] PostgreSQL uses a three-tier selectivity model per predicate: MCV lists for equality (exact frequency when value is in the list), histograms for range (equal-frequency buckets with linear interpolation within buckets), and the two are combined — MCV selectivity is computed directly, then the histogram estimates the non-MCV population, and the two are merged weighted by their respective population fractions.

- quote: "the planner applies all the conditions on items in the MCV list, and then sums the frequencies of the matching ones... the histogram is then used in the same way as above to estimate the selectivity in the portion of the table that is not MCVs, and then the two numbers are combined to estimate the overall selectivity"
- url: https://www.postgresql.org/docs/17/row-estimation-examples.html
- source_type: primary
- published: 2024 (PostgreSQL 17 docs)
- confidence: high

### [2] PostgreSQL's equality selectivity for values NOT in the MCV list uses the formula (1 - sum(mcv_freqs)) / (num_distinct - num_mcv), which distributes the remaining probability mass uniformly across non-MCV distinct values. For a column with 676 distinct values and 10 MCVs, a non-MCV equality predicate gets selectivity (1 - 0.03033) / 666 ≈ 0.00146.

- quote: "selectivity = (1 - sum(mcv_freqs))/(num_distinct - num_mcv) = (1 - (0.00333333 + 0.003 + 0.003 + 0.003 + 0.003 + 0.003 + 0.003 + 0.003 + 0.003 + 0.003))/(676 - 10) = 0.0014559"
- url: https://www.postgresql.org/docs/17/row-estimation-examples.html
- source_type: primary
- published: 2024
- confidence: high

### [3] PostgreSQL's equi-join selectivity (eqjoinsel) for unique columns uses the formula (1 - null_frac1) * (1 - null_frac2) / max(num_rows1, num_rows2), while Razordata's implementation uses 1 / max(ndv_left, ndv_right) — a simplification that omits null fraction correction but is otherwise structurally equivalent for the common case.

- quote: "selectivity = (1 - null_frac1) * (1 - null_frac2) / max(num_rows1, num_rows2) = (1 - 0) * (1 - 0) / max(10000, 10000) = 0.0001" (PostgreSQL); "selectivity = (1 - null_frac) / max(ndv_left, ndv_right, 1)" (Razordata comment in cost.go:444)
- url: https://www.postgresql.org/docs/17/row-estimation-examples.html
- source_type: primary
- published: 2024
- confidence: high

### [4] PostgreSQL's multivariate statistics (CREATE STATISTICS) address the independence assumption that causes catastrophic underestimation for correlated predicates. Without statistics objects, AND-combined predicates are multiplied independently (1% × 1% = 0.01% for a=1 AND b=1 where a=b), but with functional dependencies enabled, the planner estimates 1% — two orders of magnitude more accurate. Razordata has a correlation tracking mechanism (LearnedModel.correlations) but it is not yet integrated into multi-predicate selectivity estimation in a production-ready way.

- quote: "the planner assumes that the two conditions are independent, so that the individual selectivities of the clauses can be multiplied together: selectivity = selectivity(unique1 < 1000) * selectivity(stringu1 = 'xxx') = 0.100697 * 0.0014559 = 0.0001466" (PostgreSQL, independent); "selectivity = mcv_selectivity + histogram_selectivity * histogram_fraction = 0.01833333 + 0.298387 * 0.96966667 = 0.307669" (PostgreSQL, MCV+histogram combined)
- url: https://www.postgresql.org/docs/17/multivariate-statistics-examples.html
- source_type: primary
- published: 2024
- confidence: high

### [5] SQLite's selectivity estimation is the simplest of the three systems: ANALYZE collects NDV per index prefix column (stored in sqlite_stat1) and optionally histogram bounds (sqlite_stat3 for leftmost column, sqlite_stat4 for all columns, compile-time gated by SQLITE_ENABLE_STAT3/STAT4). Without ANALYZE, SQLite defaults to 10 duplicates per leftmost index column, which means skip-scan is never used. The cost model is not publicly parameterized.

- quote: "Without the results of ANALYZE, SQLite has to guess at the 'shape' of the data in the table, and the default guess is that there are an average of 10 duplicates for every value in the left-most column of the index. Skip-scan only becomes profitable (it only gets to be faster than a full table scan) when the number of duplicates is about 18 or more."
- url: https://www.sqlite.org/optoverview.html
- source_type: primary
- published: 2026-03-22
- confidence: high

### [6] SQLite's histogram usage (when compiled with STAT4) only aids range queries on the leftmost index column, and only when the right-hand side is a compile-time constant or parameter — it cannot help with range queries on non-leftmost index columns or expression-based predicates.

- quote: "Another limitation of the histogram data is that it only applies to the left-most column on an index... the histogram data is useless in helping to choose between the range constraints on columns x and y."
- url: https://www.sqlite.org/optoverview.html
- source_type: primary
- published: 2026-03-22
- confidence: high

### [7] Razordata's ColumnStats struct already stores both MCV lists (MostCommonVals/MostCommonFreqs) and histograms (HistogramBucket with LowerBound/UpperBound/Count), plus NDV, null count, and min/max — making it structurally comparable to PostgreSQL's pg_statistic slot system. The IN-list selectivity uses the MCV-aware formula 1 - ∏(1 - pᵢ) over matched MCV values, which is a CockroachDB/PostgreSQL-derived approach.

- quote: "REQ001057b: when the column has MCV stats, prefer the 1 - ∏(1 - pᵢ) formula over the uniform len/rowCount fallback." (cost.go:452-453); type ColumnStats struct { DistinctCount int64; NullCount int64; MinValue []byte; MaxValue []byte; Histogram []HistogramBucket; RowCount int64; MostCommonVals [][]byte; MostCommonFreqs []float64 } (ls/stats.go:7-19)
- url: /workspace/internal/SQB/EX/cost.go, /workspace/internal/ENG/LS/stats.go
- source_type: primary
- published: 2026 (current codebase)
- confidence: high

### [9] Razordata's OR-chain selectivity uses the formula 1 - ∏(1 - 1/ndv) per column group for same-column OR equalities (e.g., a=1 OR a=2 OR a=3 → 1 - (1 - 1/ndv)³), and multiplies per-column selectivities for cross-column OR. This is more sophisticated than SQLite (which either converts OR to IN or does full index union) and structurally similar to PostgreSQL's approach of summing MCV frequencies for OR-matched values.

- quote: "REQ001219: OR-chain selectivity. Same-column equality chain (a=1 OR a=2 OR ...) → group by column and use 1 - ∏(1 - 1/ndv) per column." (cost.go:515-519); test: "selectivity = 1 - (1 - 1/ndv)^k where k = number of OR equalities on the same column" (req001218_or_to_in_test.go:18)
- url: /workspace/internal/SQB/EX/cost.go, /workspace/internal/SQB/EX/req001218_or_to_in_test.go
- source_type: primary
- published: 2026
- confidence: high

### [10] The zero-row problem (empty table selectivity) is handled differently across systems: PostgreSQL scales reltuples proportionally when relpages changes (auto-detecting stale stats), SQLite returns 0 rows from the planner when statistics indicate emptiness, and Razordata explicitly guards against it — estimateRowCount skips entries where DT.Tables has an empty slice, and equality/range selectivity return fallback values (0.1/0.3) when RowCount is 0.

- quote: "REQ001192: skip 0-row entries — CREATE TABLE registers an empty slice in DT.Tables, but actual data lives in the LSM store. Returning 0 causes the planner to emit plans that produce no rows." (cost.go:335-338); PostgreSQL: "The number of pages and rows is looked up in pg_class... the planner then fetches the actual current number of pages in the table... if that is different from relpages then reltuples is scaled accordingly"
- url: /workspace/internal/SQB/EX/cost.go, https://www.postgresql.org/docs/17/row-estimation-examples.html
- source_type: primary
- published: 2026/2024
- confidence: high

### [11] Razordata's cost model coefficients match PostgreSQL's conventional defaults (seq_page_cost=1.0, random_page_cost=4.0, cpu_tuple_cost=0.01, cpu_index_tuple_cost=0.005, cpu_operator_cost=0.0025) and are tunable via SetCostParams — appropriate for an in-memory embedded engine where random I/O cost is much lower than the defaults suggest.

- quote: "Defaults match PostgreSQL's conventional values (seq_page_cost=1.0, random_page_cost=4.0, cpu_tuple_cost=0.01, cpu_index_tuple_cost=0.005, cpu_operator_cost=0.0025) but are tunable via SetCostParams so callers can adjust for specific workloads (e.g. all-in-memory tables where random I/O is cheap)." (planner.go:460-464)
- url: /workspace/internal/SQB/EX/planner.go

- published: 2026
