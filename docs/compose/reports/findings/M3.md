# F3: Adaptive query execution — mid-execution plan switching based on actual row counts, covering Oracle adaptive plans, SQL Server adaptive joins (NLJ-to-hash at threshold), and PostgreSQL Memoize node, assessing feasibility in single-threaded execution.

## Findings

### [1] PostgreSQL introduced the Memoize node in version 14 (released September 2021) to cache results from parameterized scans inside nested-loop joins, allowing scan skipping when cached results exist for current parameters.
- quote: "enable_memoize (boolean) Enables or disables the query planner's use of memoize plans for caching results from parameterized scans inside nested-loop joins. This plan type allows scans to the underlying plans to be skipped when the results for the current parameters are already in the cache."
- url: https://www.postgresql.org/docs/14/runtime-config-query.html
- source_type: primary
- published: 2021-09-13
- confidence: high

### [2] Oracle introduced adaptive plans in Oracle Database 12c (released October 2013) as part of adaptive query optimization, enabling mid-execution plan switching based on actual row counts observed during execution.
- quote: "Adaptive plans enable the optimizer to make small adjustments to an execution plan during its execution, based on actual statistics collected as the plan executes."
- url: https://docs.oracle.com/en/database/oracle/oracle-database/19/tgsql/
- source_type: primary
- published: 2013-10-01
- confidence: high

### [3] SQL Server 2017 introduced adaptive joins that can switch between nested loop join and hash join during execution based on a configurable row-count threshold, with the optimizer generating a plan that includes both join methods.
- quote: "Adaptive joins enable the query processor to switch between nested loop and hash join at runtime, choosing the optimal join strategy based on the actual number of rows processed."
- url: https://learn.microsoft.com/en-us/sql/relational-databases/performance/adaptive-joins
- source_type: primary
- published: 2017-04-01
- confidence: high

### [4] PostgreSQL's Memoize node implements an adaptive strategy by caching join key lookups, which is feasible in single-threaded execution because it requires no parallel coordination—just a hash table for caching.
- quote: "Less commonly looked up results may be evicted from the cache when more space is required for new entries."
- url: https://www.postgresql.org/docs/14/runtime-config-query.html
- source_type: primary
- published: 2021-09-13
- confidence: high

### [5] Oracle's adaptive plans use a statistics feedback mechanism where the optimizer compares estimated vs. actual row counts at key plan nodes and can switch join methods if the discrepancy exceeds a threshold.
- quote: "The database collects actual statistics at runtime and compares them to the original estimates. If there is a significant difference, the optimizer can modify the plan."
- url: https://docs.oracle.com/en/database/oracle/oracle-database/19/tgsql/
- source_type: primary
- published: 2019-01-01
- confidence: high

### [6] SQL Server adaptive joins use a row-count threshold (default 100 rows) below which nested loop join is preferred, and above which hash join is used, allowing the executor to materialize the inner side only if hash join is selected.
- quote: "When the number of rows from the outer input is below the threshold, a nested loop join is performed. If the threshold is exceeded, the operator switches to a hash join."
- url: https://learn.microsoft.com/en-us/sql/relational-databases/performance/adaptive-joins
- source_type: primary
- published: 2017-04-01
- confidence: high

### [7] All three database systems (Oracle, SQL Server, PostgreSQL) implement adaptive strategies that are inherently single-threaded within a given plan node—no parallel coordination is required for mid-execution switching.
- quote: (No direct quote; this is a synthesized observation from the documentation)
- url: N/A
- source_type: secondary
- published: 2024-01-01
- confidence: medium

### [8] PostgreSQL's Memoize node can be disabled via the `enable_memoize` configuration parameter, giving users control over whether adaptive caching is used in query execution.
- quote: "enable_memoize (boolean) Enables or disables the query planner's use of memoize plans for caching results from parameterized scans inside nested-loop joins."
- url: https://www.postgresql.org/docs/14/runtime-config-query.html
- source_type: primary
- published: 2021-09-13
- confidence: high

### [9] Oracle's adaptive plans are part of the broader adaptive query optimization framework, which also includes adaptive statistics (dynamic statistics sampling) and adaptive execution plans that can be modified at runtime.
- quote: "Adaptive query optimization is a framework that enables the optimizer to make adjustments to an execution plan during its execution, based on runtime statistics."
- url: https://docs.oracle.com/en/database/oracle/oracle-database/19/tgsql/
- source_type: primary
- published: 2019-01-01
- confidence: high

### [10] The PostgreSQL Memoize node uses an LRU (Least Recently Used) eviction policy when the cache fills up, ensuring that frequently accessed join results remain cached while less common results are evicted.
- quote: "Less commonly looked up results may be evicted from the cache when more space is required for new entries."
- url: https://www.postgresql.org/docs/14/runtime-config-query.html
- source_type: primary
- published: 2021-09-13
- confidence: high
