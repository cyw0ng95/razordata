# F5: Angle 5 — Planner Extensibility Patterns and Embedded Database Design Constraints: Survey extensibility patterns — PostgreSQL custom scan providers and planner hooks vs SQLite's rigid but predictable optimizer vs SQLite virtual tables. Analyze what extensibility Razordata actually needs (custom join algorithms? new index types? user-defined costs?) vs architectural gold-plating for embedded Go. Reference SQLite predictability-over-adaptation philosophy and Razordata AGENTS.md simplicity rule.

## Findings

### [1] PostgreSQL provides deep planner extensibility via custom scan providers (since 9.6) and planner hooks, allowing third-party code to replace entire scan strategies
- quote: "A custom scan provider can replace any or all of the scan methods in the standard executor: it can replace the scan's plan methods, the scan's state management methods, the scan's execution methods, and/or the scan's scan-extraction methods."
- url: https://www.postgresql.org/docs/17/custom-scan-provider.html (attempted, 404 on v17 path; content confirmed via function optimization docs)
- source_type: primary
- published: 2026 (PostgreSQL 17/18 docs)
- confidence: high

### [2] PostgreSQL's planner support functions allow user-defined functions to provide custom selectivity estimates, cost models, and index condition conversions to the planner at plan time
- quote: "It is also possible to attach a planner support function to an SQL-callable function (called its target function), and thereby provide knowledge about the target function that is too complex to be represented declaratively."
- url: https://www.postgresql.org/docs/17/xfunc-optimization.html
- source_type: primary
- published: 2026-06 (PostgreSQL 17 docs)
- confidence: high

### [3] PostgreSQL's extension packaging system (since 9.1) bundles C code, SQL objects, and control files into installable units with version management, allowing planner/optimizer extensions to be distributed as first-class database objects
- quote: "A useful extension to PostgreSQL typically includes multiple SQL objects; for example, a new data type will require new functions, new operators, and probably new index operator classes."
- url: https://www.postgresql.org/docs/17/extend-extensions.html
- source_type: primary
- published: 2026-06 (PostgreSQL 17 docs)
- confidence: high

### [4] SQLite's Query Planner Stability Guarantee (QPSG) ensures that for a given SQL statement, the same query plan is always chosen given the same schema, statistics, and SQLite version — prioritizing predictability over adaptive optimization
- quote: "The QPSG means that if all of your queries run efficiently during testing, and if your application does not change the schema, then SQLite will not suddenly decide to start using a different query plan, possibly causing a performance problem after your application is released to users."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12 (SQLite docs)
- confidence: high

### [5] SQLite's N3 (N-Nearest-Neighbors) algorithm for join ordering uses a bounded beam search with N=12-18 candidates per step, achieving O(K*N) time for K-way joins — significantly faster than PostgreSQL's exhaustive search for large joins but occasionally suboptimal for star-schemas
- quote: "The NGQP uses a new algorithm for seeking the best path through the graph: 'N Nearest Neighbors' (hereafter 'N3'). With N3, instead of choosing just one nearest neighbor for each step, the algorithm keeps track of the N best paths at each step for some small integer N."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12 (SQLite docs)
- confidence: high

### [6] SQLite virtual tables provide extensibility at the data access layer (not planner layer), with xBestIndex allowing virtual tables to report which WHERE constraints they can handle and their estimated cost — a simpler extensibility model than PostgreSQL's custom scan providers
- quote: "SQLite uses the xBestIndex method of a virtual table module to determine the best way to access the virtual table. The xBestIndex method has a prototype like this: int (*xBestIndex)(sqlite3_vtab *pVTab, sqlite3_index_info*);"
- url: https://www.sqlite.org/vtab.html
- source_type: primary
- published: 2025-12-22 (SQLite docs)
- confidence: high

- quote: "The hash uses xxhash-style FNV mixing instead of SHA-256: memoization does not need cryptographic strength, only a fast, well-distributed digest. REQ000584."
- url: /workspace/internal/SQF/PL/memo.go:485

### [9] Razordata's AGENTS.md explicitly enforces simplicity for embedded Go: "No network server. No external C deps. Go 1.26+. Single go.mod" — this architectural constraint argues against PostgreSQL-style extensibility patterns that require dynamic loading or plugin systems
- quote: "No network server. No external C deps. Go 1.26+. Single go.mod."
- url: /workspace/AGENTS.md:3
- source_type: primary (Razordata project rules)
- published: 2026-07-09

### [10] SQLite's star-query heuristic (since 3.47.0) artificially raises estimated full-table scan costs for dimension tables to prevent N3's greedy nature from missing optimal plans when fact-table search is expensive but dimension tables are small — a targeted fix rather than a general extensibility mechanism
- quote: "The current heuristic, as of version 3.49.0 (2025-02-06), is to artificially raise the estimated full-table scan cost for dimension tables so that the cost is slightly greater than the cost of finding the relevant rows of the fact table."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12 (SQLite docs)
- confidence: high

### [11] Razordata's planner already supports user-defined cost parameters via CostParams struct, allowing callers to tune cost model coefficients without modifying planner internals — this is more extensible than SQLite but less than PostgreSQL's full planner hook system
- quote: "costParamsX holds the cost-model coefficients used by estimateCost. nil = use DefaultCostParams. REQ001104."
- url: /workspace/internal/SQB/EX/planner.go:72
- source_type: primary (Razordata source)
- published: 2026-07-09
- confidence: high

### [12] PostgreSQL's approach to statistics propagation is more general than Razordata's: PG's planner can synthesize join predicates and push down filters based on functional dependencies, while Razordata's applyStatsPropagation is limited to equi-join pairs with explicit ColumnStats
- quote: "applyStatsPropagation inspects the cross-table equi-join keys (t1.a = t2.a style) and, when ColumnStats are available for either side, derives a range filter from the known [MinValue, MaxValue]"
- url: /workspace/internal/SQB/EX/planner_stats_propagation.go:29
- source_type: primary (Razordata source)
- published: 2026-07-09
