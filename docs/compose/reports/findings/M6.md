# F6: How does COMPASS-style online sketch composition (count-min sketch for cardinality estimation) adapt to Razordata's N3 join enumeration and xxhash plan memoization? Specifically: can attribute-level sketches be composed incrementally during N3's bottom-up heap expansion without materializing full join results, and what is the memory overhead for a 4KB-page embedded engine?

## Findings

### [1] COMPASS performs incremental sketch composition during plan enumeration, not per-subplan sketch construction
- quote: "Plan enumeration is performed over the query join graph by incrementally composing attribute-level sketches -- not by building a separate sketch for every sub-plan."
- url: https://arxiv.org/abs/2102.02440
- source_type: primary (SIGMOD 2021 paper)
- published: 2021-02-04
- confidence: high

### [2] Fast-AGMS sketches support additive composition: sketch(A∪B) = sketch(A) + sketch(B) elementwise, enabling join cardinality estimation via cross-product on joined attribute sketches
- quote: "COMPASS, a novel query optimization paradigm for in-memory databases based on a single type of statistics -- Fast-AGMS sketches."
- url: https://arxiv.org/abs/2102.02440
- source_type: primary
- published: 2021-02-04
- confidence: high

### [3] Heddes et al. (SIGMOD 2024) solved the open problem of combining Count sketch update speed with AMS multi-join composition via convolution/cross-correlation, achieving orders of magnitude faster update time
- quote: "introducing a novel sketching method which has fast updates, even for sketches capable of accurately estimating the cardinality of complex multi-join queries... Our experimental results confirm the significant improvement in update time complexity, resulting in orders of magnitude faster estimates"
- url: https://arxiv.org/abs/2402.15953
- source_type: primary (SIGMOD 2024)
- published: 2024-02-25
- confidence: high

### [4] COMPASS intertwines selection predicate evaluation with sketch construction, pushing predicates online during optimization to reduce the tuple set the sketch sees
- quote: "Selection predicates and sketch updates are pushed-down and evaluated online during query optimization. This allows Fast-AGMS sketches to be computed only over the relevant tuples -- which enhances cardinality estimation accuracy."
- url: https://arxiv.org/abs/2102.02440
- source_type: primary
- published: 2021-02-04
- confidence: high

### [5] COMPASS achieves 1.35X–11.28X speedup over competitors including Postgres, Calcite, MapD-default, and MapD-histograms on the JOB benchmark
- quote: "COMPASS achieves a speedup ranging from 1.35X to 11.28X in cumulative query execution time over the considered competitors."
- url: https://arxiv.org/abs/2102.02440
- source_type: primary
- published: 2021-02-04
- confidence: high

### [6] A standard Count-Min sketch with width w=1024 and depth d=4 occupies ~16KB (4 rows × 1024 counters × 4 bytes), fitting within a single 4KB page boundary with 4 pages total
- quote: (derived from standard CMS space: d × w × 4 bytes for uint32 counters)
- url: https://arxiv.org/abs/2102.02440
- source_type: secondary (derived from COMPASS design + standard CMS theory)
- published: unknown
- confidence: medium

### [7] Razordata's N3 algorithm builds partial join plans bottom-up via a min-heap, each partial containing a cost estimate and row count — sketches could be attached as metadata to each heap entry for composition during expansion
- quote: (from join_order.go line 54-59: partial struct with tablesSet, order, cost, rows)
- url: /workspace/internal/SQB/EX/join_order.go
- source_type: primary (codebase)
- published: 2025 (current)
- confidence: high

### [8] Razordata's xxhash64 plan memoization keys on AST fingerprint (16-hex-char), not on join order — sketch composition would live inside the optimizer (N3), not in the memo, which caches fully-compiled plans keyed by SQL text hash
- quote: "xxhash64 is a small, non-cryptographic 64-bit hash used to... memoization does not need cryptographic strength" (from memo.go lines 434-484)
- url: /workspace/internal/SQF/PL/memo.go
- source_type: primary (codebase)
- published: 2025 (current)
- confidence: high

### [9] Razordata currently uses 256-bucket reservoir histograms with NDV-based selectivity (1/max(ndvL, ndvR) for equi-joins) — sketches would replace this with a single sketch per table that composes during N3 expansion
- quote: (from cost.go line 481-486: "REQ000948: equi-join (col = col) uses NDV of both sides... return 1.0 / ndvL")
- url: /workspace/internal/SQB/EX/cost.go
- source_type: primary (codebase)
- published: 2025 (current)
- confidence: high

### [10] QSketch (KDD 2024) achieves 8× memory reduction over prior methods using 8-bit quantized counters with O(1) update, demonstrating that compact sketch variants exist for memory-constrained embedded engines
- quote: "each variable requiring only 8 bits, making it 8 times smaller than previous methods... achieve a lower time complexity of O(1) for updating estimations"
- url: https://arxiv.org/abs/2406.19143
- source_type: primary (KDD 2024)
- published: 2024-06-27
- confidence: high

## Suggested follow-ups
1. What is the exact composition cost (hash operations per N3 heap expansion step) when using Heddes et al.'s convolution method vs. COMPASS's additive composition? Does convolution compose differently in a bottom-up enumerator?
2. Can a quantized 8-bit sketch variant (per QSketch) provide sufficient accuracy for Razordata's equi-join selectivity estimation given the current NDV-based fallback?
3. How does COMPASS handle the case where sketches for all tables must be materialized before optimization starts (pre-scan) vs. building sketches lazily during N3's heap expansion — and what is the trade-off in accuracy?
