# F7: SQLite vs PostgreSQL query plan optimizers — architecture, differences, and Razordata adoption priorities

## Findings

### [1] SQLite's NGQP uses N3 (N Nearest Neighbors) for join ordering — O(K×N²) time vs PostgreSQL's exhaustive K! search for small joins
- quote: "The NGQP uses a new algorithm for seeking the best path through the graph: 'N Nearest Neighbors' (hereafter 'N3'). With N3, instead of choosing just one nearest neighbor for each step, the algorithm keeps track of the N bests paths at each step for some small integer N."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12 (NGQP doc last updated)
- confidence: high

### [2] SQLite's N3 uses N=12 for general joins, N=18 for star-schema joins (as of v3.49.0) — Razordata uses N=24 heap size with 2.0x pruning multiplier
- quote: "The initial implementation of NGQP chooses N=1 for simple queries, N=5 for two-way joins and N=10 for all joins with three or more tables. Later, the N value for joins with three or more tables was raised to 12 or to 18 if the join is against a star-schema."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [3] PostgreSQL uses three join strategies (nested loop, merge join, hash join) vs SQLite's nested-loop-only — Razordata already supports all three
- quote: "The three available join strategies are: nested loop join, merge join, hash join."
- url: https://www.postgresql.org/docs/current/planner-optimizer.html
- source_type: primary
- published: unknown
- confidence: high

### [4] PostgreSQL's GEQO (Genetic Query Optimizer) kicks in at geqo_threshold=12 joins, using genetic algorithm with configurable pool/generations — SQLite never uses this approach, preferring N3's deterministic search
- quote: "Use genetic query optimization to plan queries with at least this many FROM items involved. The default is 12."
- url: https://www.postgresql.org/docs/current/runtime-config-query.html
- source_type: primary
- published: unknown
- confidence: high

### [5] PostgreSQL stores rich per-column statistics (histogram_bounds, most_common_vals, most_common_freqs, n_distinct, null_frac) in pg_statistic with configurable target (default 100) — SQLite stores only sqlite_stat1 (index b-tree depth/leaf pages) and optionally sqlite_stat3/stat4 histograms
- quote: "The amount of information stored in pg_statistic by ANALYZE, in particular the maximum number of entries in the most_common_vals and histogram_bounds arrays for each column, can be set on a column-by-column basis using the ALTER TABLE SET STATISTICS command, or globally by setting the default_statistics_target configuration variable. The default limit is presently 100 entries."
- url: https://www.postgresql.org/docs/current/planner-stats.html
- source_type: primary
- published: unknown
- confidence: high

### [6] PostgreSQL supports multivariate extended statistics (functional dependencies, N-distinct counts, MCV lists) for correlated columns — neither SQLite nor Razordata has this capability
- quote: "It is common to see slow queries running bad execution plans because multiple columns used in the query clauses are correlated. The planner normally assumes that multiple conditions are independent of each other, an assumption that does not hold when column values are correlated."
- url: https://www.postgresql.org/docs/current/planner-stats.html
- source_type: primary
- published: unknown
- confidence: high

### [7] Razordata's N3 implementation (join_order.go:11-273) already implements multi-start N3 with per-table selectivity pre-computation, predicate caching, and cost-based pruning — closely mirrors SQLite's NGQP approach
- quote: "REQ000946: n3JoinOrderingMultiStart runs the N3 algorithm from every candidate base table (the leftmost table in FROM plus each subsequent table) and returns the lowest-cost plan."
- url: /workspace/internal/SQB/EX/join_order.go
- source_type: primary (codebase)
- published: 2026-07-09
- confidence: high

### [8] Razordata's cost model (cost.go:465-484) already uses PostgreSQL-style parameters (seqPageCost=1.0, randomPageCost=4.0, cpuTupleCost=0.01) — tunable via SetCostParams for embedded workloads
- quote: "CostParams captures the cost-model coefficients used by estimateCost. REQ001104. Defaults match PostgreSQL's conventional values (seq_page_cost=1.0, random_page_cost=4.0, cpu_tuple_cost=0.01, cpu_index_tuple_cost=0.005, cpu_operator_cost=0.0025) but are tunable via SetCostParams."
- url: /workspace/internal/SQB/EX/planner.go
- source_type: primary (codebase)
- published: 2026-07-09
- confidence: high

### [9] Razordata's selectivity estimation uses NDV-based equality (1/NDV), histogram range queries, MCV-based IN-list selectivity, and OR-chain formula `1 - (1 - 1/ndv)^k` — more sophisticated than SQLite's uniform 10-row default but lacks PostgreSQL's multivariate statistics
- quote: "REQ000948: NDV-based join predicate selectivity. Method variant of ColumnStats.DistinctCount for column-specific NDV values."
- url: /workspace/internal/SQB/EX/cost.go
- source_type: primary (codebase)
- published: 2026-07-09
- confidence: high

### [10] SQLite's star-query heuristic (v3.49.0) artificially raises dimension-table full-scan costs to prevent N3 from greedily selecting cheap dimension scans and pushing out the expensive fact-table search — Razordata has no equivalent star-schema awareness in its N3 implementation
- quote: "The current heuristic, as of version 3.49.0 (2025-02-06), is to artificially raise the estimated full-table scan cost for dimension tables so that the cost is slightly greater than the cost of finding the relevant rows of the fact table."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-02-06
- confidence: high

### [11] PostgreSQL's Memoize plan node caches parameterized nested-loop join results to avoid repeated inner scans — Razordata's plan cache is statement-level (AST fingerprint LRU), not per-parameter-value like PostgreSQL's Memoize
- quote: "enable_memoize: Enables or disables the query planner's use of memoize plans for caching results from parameterized scans inside nested-loop joins."
- url: https://www.postgresql.org/docs/current/runtime-config-query.html
- source_type: primary
- published: unknown
- confidence: high

### [12] SQLite guarantees plan stability (QPSG) — same schema + same ANALYZE = same plan across runs — PostgreSQL does not make this guarantee since statistics evolve with data changes; Razordata's plan cache (AST fingerprint LRU) implicitly provides similar stability for repeated queries
- quote: "The QPSG means that if all of your queries run efficiently during testing, and if your application does not change the schema, then SQLite will not suddenly decide to start using a different query plan."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

## Suggested follow-ups
1. **Star-schema heuristic for Razordata**: SQLite v3.49.0 raised dimension-table scan costs in N3 to avoid greedy starvation of fact-table plans. Razordata's N3 (join_order.go) has no equivalent — should we add fact/dimension heuristics for star queries?
2. **Multivariate statistics (extended stats)**: PostgreSQL's functional dependencies, N-distinct, and MCV lists for correlated columns significantly improve selectivity estimates. Razordata currently assumes column independence. Worth prioritizing?
3. **Parameterized Memoize node**: PostgreSQL caches nested-loop join results by parameter values (enable_memoize). Razordata's plan cache is statement-level. A per-parameter-value cache inside nested loops could reduce repeated inner scans for correlated subqueries.
