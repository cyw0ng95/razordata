# F8: SQLite/PostgreSQL optimizer architecture differences and Razordata adoption priorities

## Findings

### [1] Razordata's N3 join ordering already mirrors SQLite NGQP's N-nearest-neighbor algorithm with identical structure
- quote: "The NGQP uses a new algorithm for seeking the best path through the graph: 'N Nearest Neighbors' (hereafter 'N3'). With N3, instead of choosing just one nearest neighbor for each step, the algorithm keeps track of the N bests paths at each step for some small integer N."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [2] SQLite NGQP uses N=12 (general) / N=18 (star schemas) while Razordata uses N=24 heap size — Razordata's N is more aggressive
- quote: "The initial implementation of NGQP chooses N=1 for simple queries, N=5 for two-way joins and N=10 for all joins with three or more tables. Later, the N value for joins with three or more tables was raised to 12 or to 18 if the join is against a star-schema."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [3] SQLite NGQP only supports nested loop joins; Razordata already goes beyond by supporting hash join, merge join, and hash cross join with cost-based selection
- quote: "SQLite computes joins using nested loops, one loop for each table in the join." / "The three available join strategies are: nested loop join, merge join, hash join" (PostgreSQL)
- url: https://www.sqlite.org/queryplanner-ng.html / https://www.postgresql.org/docs/17/planner-optimizer.html
- source_type: primary
- published: 2025-07-12 / 2024-11-01
- confidence: high

### [4] PostgreSQL uses dynamic programming for ≤geqo_threshold (default 12) tables, then genetic algorithm (GEQO); Razordata uses N3 with multi-start for all sizes and exhaustive for ≤4 tables
- quote: "When the number of joins exceeds a threshold (see geqo_threshold), PostgreSQL uses a Genetic Query Optimizer." / "All possible plans are generated for every join pair considered by the planner"
- url: https://www.postgresql.org/docs/17/planner-optimizer.html / https://www.postgresql.org/docs/17/geqo.html
- source_type: primary
- published: 2024-11-01
- confidence: high

### [5] SQLite's star-query heuristic (v3.49+) artificially raises dimension table full-scan costs to prevent N3 from eliminating fact-table searches early; Razordata detects bushy joins but lacks this cost adjustment
- quote: "The current heuristic, as of version 3.49.0 (2025-02-06), is to artificially raise the estimated full-table scan cost for dimension tables so that the cost is slightly greater than the cost of finding the relevant rows of the fact table."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [6] Razordata's CostParams defaults match PostgreSQL's conventional values exactly (seq_page_cost=1.0, random_page_cost=4.0, cpu_tuple_cost=0.01)
- quote: "DefaultCostParams returns: SeqPageCost=1.0, RandomPageCost=4.0, CPUTupleCost=0.01, CPUIndexTupleCost=0.005, CPUOperatorCost=0.0025" (Razordata source)
- url: /workspace/internal/SQB/EX/planner.go
- source_type: primary
- published: 2026-07-09
- confidence: high

### [7] Razordata uses xxhash64 for memoization keys (NOT SHA256), with parameterized keys that normalize literals to Param nodes — faster than SQLite's approach and more sophisticated than PostgreSQL (which has no plan memoization)
- quote: "SerializeKey returns a stable 16-hex-character fingerprint of an AST, mixing in the current schema version... The hash uses xxhash-style FNV mixing instead of SHA-256: memoization does not need cryptographic strength, only a fast, well-distributed digest." (Razordata source)
- url: /workspace/internal/SQF/PL/memo.go
- source_type: primary
- published: 2026-07-09
- confidence: high

### [8] PostgreSQL's NDV-based join selectivity formula is selectivity = (1 - null_frac) / max(ndv_left, ndv_right); Razordata already implements this exact formula (REQ000948)
- quote: "PostgreSQL reference (eqjoinsel): selectivity = (1 - null_frac) / max(ndv_left, ndv_right, 1)." (Razordata source)
- url: /workspace/internal/SQB/EX/cost.go
- source_type: primary
- published: 2026-07-09
- confidence: high

### [9] SQLite stores statistics in SQLITE_STAT1 table via ANALYZE; PostgreSQL uses pg_statistic with histograms, MCVs, and per-column distinct counts; Razordata has ColumnStats with Histogram, MostCommonVals, MostCommonFreqs, DistinctCount, NullCount — matching PostgreSQL's richness
- quote: "SQLite's ANALYZE command gathers statistics on the quality of the various indexes and stores those statistics in the SQLITE_STAT1 table." / Razordata's ls.ColumnStats contains DistinctCount, NullCount, Histogram, MostCommonVals, MostCommonFreqs
- url: https://www.sqlite.org/queryplanner-ng.html / /workspace/internal/ENG/LS/
- source_type: primary
- published: 2025-07-12 / 2026-07-09
- confidence: high

### [10] Razordata's MCV-aware IN-list selectivity (1 - ∏(1 - pᵢ) + uniform tail) matches CockroachDB/PostgreSQL semantics and goes beyond SQLite which has no MCV support
- quote: "REQ001057b: matches CockroachDB / PostgreSQL semantics — when MCVs are known, the per-element frequency is used for matching values, and a uniform tail (remaining list count) / (NDV - MCV count) accounts for rare values." (Razordata source)
- url: /workspace/internal/SQB/EX/cost.go
- source_type: primary
- published: 2026-07-09
- confidence: high

### [11] PostgreSQL's extensibility (custom scan providers, extension hooks, GEQO) is architecture-level; Razordata's embedded Go design means extensibility comes via Go interfaces (DT.Operator, StatsCatalog) rather than loadable modules — appropriate for the target use case
- quote: "Extensible via custom scan providers, extension hooks" / Razordata's DT.Operator interface and pl.StatsCatalog interface provide Go-native extensibility
- url: https://www.postgresql.org/docs/17/planner-optimizer.html / /workspace/docs/design/ARCH.md
- source_type: primary
- published: 2024-11-01 / 2026-07-09
- confidence: high

### [12] Razordata's multi-start N3 strategy (trying every table as base) matches SQLite's later improvements where the planner considers multiple starting points, but Razordata already runs K × K² × H evaluations for K tables — bounded and practical
- quote: "REQ000946: n3JoinOrderingMultiStart runs the N3 algorithm from every candidate base table... For a query with K FROM-tables, the cost is K × K² × H evaluations where H=n3HeapMaxSize=24. With K=8 this is ~1536 evaluations — negligible compared to execution time." (Razordata source)
- url: /workspace/internal/SQB/EX/join_order.go
- source_type: primary
- published: 2026-07-09
- confidence: high
