# F2: Angle 2 — PostgreSQL Query Optimizer Source Architecture: Source-level analysis of PostgreSQL's join ordering (DP for small plans, GEQO genetic algorithm for large), cost model (cpu_tuple_cost, seq_page_cost, random_page_cost, etc.), statistics (pg_statistic with MCV lists, histograms, correlation), join algorithm selection (nested loop, hash, merge with cost-based switching), and extensibility (custom scan providers, planner_hook, join_search_hook). Focus: what PostgreSQL's generality costs and where complexity pays off.

## Findings

### [1] PostgreSQL uses a dual join-ordering strategy: exhaustive dynamic programming for ≤12 tables, genetic algorithm (GEQO) for larger queries
- quote: "If the query uses fewer than geqo_threshold relations, a near-exhaustive search is conducted to find the best join sequence. When geqo_threshold is exceeded, the join sequences considered are determined by heuristics, as described in Chapter 60."
- url: https://www.postgresql.org/docs/17/planner-optimizer.html
- source_type: primary
- published: 2024-09-26 (PostgreSQL 17 docs)
- confidence: high

### [2] GEQO is a genetic algorithm with configurable pool size (default 100-1000 individuals), generations, and selection bias (1.50-2.00)
- quote: "The genetic query optimizer (GEQO) is an algorithm that does query planning using heuristic searching. This reduces planning time for complex queries (those joining many relations), at the cost of producing plans that are sometimes inferior to those found by the normal exhaustive-search algorithm."
- url: https://www.postgresql.org/docs/17/geqo-intro.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [3] PostgreSQL's cost model uses relative units with seq_page_cost=1.0 as baseline; random_page_cost=4.0, cpu_tuple_cost=0.01, cpu_index_tuple_cost=0.005, cpu_operator_cost=0.0025
- quote: "Only their relative values matter, hence scaling them all up or down by the same factor will result in no change in the planner's choices. By default, these cost variables are based on the cost of sequential page fetches; that is, seq_page_cost is conventionally set to 1.0"
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [4] Statistics use MCV (Most Common Values) lists for exact equality estimates, equal-frequency histograms for range selectivity, and correlation for index scans
- quote: "For equality estimation the histogram is not useful; instead the list of most common values (MCVs) is used to determine the selectivity."
- url: https://www.postgresql.org/docs/17/row-estimation-examples.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [5] Join selectivity estimation uses MCV list comparison when both columns have MCVs, otherwise falls back to (1-null_frac1)*(1-null_frac2)/max(num_rows1,num_rows2) for unique columns
- quote: "In this case there is no MCV information for unique2 and all the values appear to be unique (n_distinct = -1), so we use an algorithm that relies on the row count estimates for both relations"
- url: https://www.postgresql.org/docs/17/row-estimation-examples.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [6] PostgreSQL supports four planner hooks: planner_hook (full control), planner_setup_hook (after PlannerGlobal init), planner_shutdown_hook (before cleanup), create_upper_paths_hook (upper-rel paths)
- quote: "/* Hook for plugins to get control in planner() */ planner_hook_type planner_hook = NULL; /* Hook for plugins to get control after PlannerGlobal is initialized */ planner_setup_hook_type planner_setup_hook = NULL;"
- url: https://raw.githubusercontent.com/postgres/postgres/master/src/backend/optimizer/plan/planner.c
- source_type: primary
- published: 2026-07-09 (latest source)
- confidence: high

### [7] The planner generates Path structures (not full Plan nodes) during optimization, only materializing the cheapest Path into a Plan tree at the end
- quote: "The planner's search procedure actually works with data structures called paths, which are simply cut-down representations of plans containing only as much information as the planner needs to make its decisions. After the cheapest path is determined, a full-fledged plan tree is built to pass to the executor."
- url: https://www.postgresql.org/docs/17/planner-optimizer.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [8] Three join algorithms are available: nested-loop (with index), merge (requires sort or index), and hash (builds hash table from right relation)
- quote: "nested loop join: The right relation is scanned once for every row found in the left relation... merge join: Each relation is sorted on the join attributes before the join starts... hash join: the right relation is first scanned and loaded into a hash table"
- url: https://www.postgresql.org/docs/17/planner-optimizer.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [9] Parallel query support adds parallel_setup_cost=1000 and parallel_tuple_cost=0.1; minimum scan sizes are 8MB for tables and 512KB for indexes
- quote: "parallel_setup_cost (floating point) — Sets the planner's estimate of the cost of launching parallel worker processes. The default is 1000."
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [10] effective_cache_size (default 4GB) influences index vs seq-scan decisions by estimating available disk cache
- quote: "Sets the planner's assumption about the effective size of the disk cache that is available to a single query. This is factored into estimates of the cost of using an index; a higher value makes it more likely index scans will be used"
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [11] The default_statistics_target=100 controls histogram/MCV granularity; larger values improve accuracy but increase ANALYZE time
- quote: "Sets the default statistics target for table columns without a column-specific target set via ALTER TABLE SET STATISTICS. Larger values increase the time needed to do ANALYZE, but might improve the quality of the planner's estimates."
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-09-26
- confidence: high

### [12] GEQO was developed at University of Mining and Technology in Freiberg, Germany for decision support queries with many joins that made exhaustive search infeasible
- quote: "The Institute of Automatic Control at the University of Mining and Technology, in Freiberg, Germany, encountered some problems when it wanted to use PostgreSQL as the backend for a decision support knowledge based system for the maintenance of an electrical power grid."
- url: https://www.postgresql.org/docs/17/geqo-intro.html
- source_type: primary
- published: 2024-09-26
- confidence: high
