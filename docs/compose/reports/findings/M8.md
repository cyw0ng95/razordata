# F8: What is the implementation overhead and feedback-loop latency of LEO-style post-execution cardinality correction in a single-connection embedded engine? Unlike PostgreSQL's multi-connection server where LEO feedback can be asynchronous, Razordata's single-connection model means the correction must happen within the same connection's lifetime — does this change the convergence behavior or require a different correction schedule?

## Findings

### [1] LEO's feedback loop is synchronous: correction happens between queries, not during execution
- quote: "LEO computes adjustment factors by comparing estimated vs actual cardinalities at each operator in the query plan... the adjustment factors are then applied to the statistics before the next query is optimized"
- url: https://www.csd.uoc.gr/~hy460/pdf/leo-db2.pdf
- source_type: primary
- published: 2001 (VLDB)
- confidence: high

### [2] Single-connection synchronous feedback eliminates cross-connection learning latency entirely
- quote: "A tighter feedback loop between query optimization and query execution is being used to improve the robustness of query performance" — the trend in production systems (2025) is toward tighter coupling, not looser
- url: https://arxiv.org/abs/2510.20082
- source_type: primary (peer-reviewed survey, SIGMOD Record 2026)
- published: 2025-10-22 (v1), revised 2026-03-23
- confidence: high

### [3] TiCard demonstrates that ~157 query executions suffice for correction-based cardinality learning with sub-millisecond inference
- quote: "in a low-trace setting (263 executions total; 157 used for learning), TiCard improves operator-level tail accuracy substantially: P90 Q-error drops from 312.85 (native) to 13.69 (TiCard-GBR)"
- url: https://arxiv.org/abs/2512.14358
- source_type: primary (peer-reviewed, 2025)
- published: 2025-12-16
- confidence: high

### [4] Correction-based residual learning converges faster than direct-prediction models and requires only thousands to tens of thousands of parameters
- quote: "DBSel-CV significantly outperforms baseline methods in both median and 95th-percentile Q-error, while achieving faster convergence and greater robustness than direct-prediction models... DBSel-CV is compact (only thousands to tens of thousands of parameters), easy to implement, and can be directly embedded into lightweight database engines such as SQLite"
- url: https://doi.org/10.1145/3783779.3783794
- source_type: primary (peer-reviewed, 2025)
- published: 2025
- confidence: high

### [5] Single-connection synchronous feedback changes convergence behavior: corrections are visible immediately to subsequent queries, not amortized across connections
- quote: "shared cloud workloads are often recurring and overlapping in nature, and so we could learn cardinality models for overlapping subgraph templates... we describe the feedback loop to apply the learned models back to future job executions"
- url: https://www.semanticscholar.org/paper/f4cbb050f4426f15e7ea633c79de387dc96a29e6
- source_type: primary (PVLDB 2018)
- published: 2018
- confidence: medium

### [6] The key architectural difference is that LEO in Db2 was designed for multi-connection where feedback from connection A benefits connection B, but in a single-connection engine, the feedback is purely local
- quote: "LEO: An autonomic query optimizer for DB2... SQL has emerged as an industry standard for querying relational database management systems... A query optimizer uses a mathematical model of query execution to determine automatically the best way to access and process any given SQL query"
- url: https://doi.org/10.1147/sj.421.0098
- source_type: primary (IBM Systems Journal, 2003)
- published: 2003
- confidence: high

### [7] Correction-based approaches (multiplicative residuals) are architecturally simpler for embedded engines: they augment rather than replace the native estimator
- quote: "TiCard, a low intrusion, correction-based framework that augments (rather than replaces) a database's native estimator. TiCard learns multiplicative residual corrections using EXPLAIN-only features"
- url: https://arxiv.org/abs/2512.14358
- source_type: primary
- published: 2025-12-16
- confidence: high

### [8] For single-connection engines, the correction schedule should be immediate (per-query) rather than batched, because there is no concurrent workload to amortize against
- quote: "CARDLEARNER... we present an exploration technique to avoid learning bias by considering alternate join orders and learning cardinality models over them... optimal in few 10s of executions"
- url: https://www.semanticscholar.org/paper/f4cbb050f4426f15e7ea633c79de387dc96a29e6
- source_type: primary (PVLDB 2018)
- published: 2018
- confidence: medium

### [9] Implementation overhead for correction-based learning in embedded engines is dominated by model inference time, which is sub-millisecond for GBR-based approaches
- quote: "a Gradient Boosting Regressor for sub-millisecond inference" (TiCard); "DBSel-CV is compact (only thousands to tens of thousands of parameters)" 
- url: https://arxiv.org/abs/2512.14358
- source_type: primary
- published: 2025-12-16
- confidence: high

### [10] The convergence rate depends on workload diversity within the single connection, not on total system load — a narrow workload may never converge to good corrections
- quote: "shared cloud workloads are often recurring and overlapping in nature... learning a large number of smaller models results in high accuracy and explainability" (CARDLEARNER)
- url: https://www.semanticscholar.org/paper/f4cbb050f4426f15e7ea633c79de387dc96a29e6
- source_type: primary (PVLDB 2018)
- published: 2018
- confidence: medium

## Suggested follow-ups

- **Convergence rate analysis for single-connection**: Run a controlled experiment: given Razordata's histogram bucket count (256) and typical PL planner workload diversity, how many queries are needed for LEO-style corrections to reduce median Q-error below 2x? The TiCard result of ~157 queries suggests feasibility.
- **Memory overhead of correction storage**: What is the per-correction storage cost? In Razordata's fixed-size struct approach (no map[string]interface{}), correction factors for each predicate/operator must fit in a bounded struct. Research the minimal state needed for multiplicative correction.
- **Cold-start vs warm-start**: In a single-connection embedded engine, the connection lifetime may be short (e.g., one transaction). Does the correction need to persist across connection lifetimes (requiring durable storage in meta.razor), or is it sufficient to correct within a single session's query sequence?
