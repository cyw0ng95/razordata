# F3: Angle 3 — Razordata SQF/PL Architecture Assessment: Map current planner internals — N3 join ordering with multi-start (K<=4), pickCheaperScan, estimateJoinCost, joinPredSel (NDV-based), StatsCatalog (NDV, rowcount, histograms via ColumnStats), plan memoization SHA256, razor_stat1 — to SQLite/PostgreSQL counterparts. Produce a gap matrix: [Razordata component] -> [SQLite equivalent] -> [PostgreSQL equivalent] -> [missing capability].

## Findings

### [1] Razordata's N3 join ordering with multi-start (K<=8) already exceeds SQLite's N3 in structural sophistication but lacks SQLite's star-query cost-adjustment heuristic.
- SQLite NGQP (v3.8.0+, 2013) introduced the N3 algorithm with N=10-18 for 3+ table joins; the latest version (3.49.0, 2025-02-06) raises full-table-scan cost for dimension tables to prevent them from pushing fact-table searches out of the N-best heap early. Razordata's N3 uses N=24 heap size (`n3HeapMaxSize=24`) and multi-start (every candidate base table tried), but its star-query support is limited to bushy-group detection (`groupBushyJoins`) without the cost-inflation heuristic.
- quote: "The current heuristic, as of version 3.49.0 (2025-02-06), is to artificially raise the estimated full-table scan cost for dimension tables so that the cost is slightly greater than the cost of finding the relevant rows of the fact table."
- url: https://www.sqlite.org/queryplanner-ng.html
- source_type: primary
- published: 2025-07-12
- confidence: high

### [2] PostgreSQL uses dynamic programming for joins ≤12 tables (geqo_threshold default) and genetic algorithm (GEQO) for larger joins, fundamentally different from Razordata's N3 approach.
- PostgreSQL's dynamic programming exhaustively considers all join orders up to `geqo_threshold` (default 12) tables, producing optimal plans for moderate joins. For 13+ tables, GEQO uses a genetic algorithm with configurable pool_size (100-1000) and generations. Razordata's N3 is O(K×N) with N=24, which is faster than PG's exponential DP but may miss optimal plans that DP guarantees for K≤12.
- quote: "Use genetic query optimization to plan queries with at least this many FROM items involved. ... The default is 12."
- url: https://www.postgresql.org/docs/17/runtime-config-query.html
- source_type: primary
- published: 2024-10-01
- confidence: high

### [3] Razordata's joinPredSel NDV-based selectivity already matches PostgreSQL's eqjoinsel formula: selectivity = 1/max(ndv_left, ndv_right).
- Razordata's `joinPredSel` method (REQ000948) implements `1/max(ndvL, ndvR)` for equality predicates, directly matching PostgreSQL's `eqjoinsel` standard function. Both fall back to 0.1 when NDV is unavailable. Razordata also handles OR-chain selectivity via the `1 - ∏(1 - 1/ndv)^k` formula (REQ001219), which aligns with PostgreSQL's approach.
- quote: "For equi-join (col = col) uses NDV of both sides. REQ000948: when stats are unavailable, use the table's row count as NDV proxy."
- url: (internal source: internal/SQB/EX/cost.go)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [4] Razordata's CostParams defaults are identical to PostgreSQL's planner cost constants, but Razordata lacks effective_cache_size and parallel cost parameters.
- Razordata's `DefaultCostParams()` returns SeqPageCost=1.0, RandomPageCost=4.0, CPUTupleCost=0.01, CPUIndexTupleCost=0.005, CPUOperatorCost=0.0025 — exactly matching PostgreSQL's defaults. However, Razordata lacks `effective_cache_size` (PG default 4GB, used to adjust index vs seqscan tradeoff), `parallel_setup_cost` (1000), and `parallel_tuple_cost` (0.1). The code comments confirm: "Defaults match PostgreSQL's conventional values (REQ001104)."
- quote: "CostParams captures the cost-model coefficients used by estimateCost. REQ001104. Defaults match PostgreSQL's conventional values (seq_page_cost=1.0, random_page_cost=4.0, cpu_tuple_cost=0.01, cpu_index_tuple_cost=0.005, cpu_operator_cost=0.0025)."
- url: (internal source: internal/SQB/EX/planner.go:465-484)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [5] Razordata's ColumnStats (NDV, null count, histogram, MCV) covers the same data as SQLite's sqlite_stat1/stat3/stat4 and PostgreSQL's pg_statistic, but lacks correlation and extended statistics.
- Razordata's `ColumnStats` struct stores DistinctCount, NullCount, MinValue, MaxValue, Histogram (256 equi-depth buckets), MostCommonVals, and MostCommonFreqs. SQLite's sqlite_stat1 stores per-index-prefix NDV; sqlite_stat3/stat4 adds histograms (leftmost or all columns). PostgreSQL's pg_statistic stores n_distinct, most_common_vals, most_common_freqs, histogram_bounds, and correlation. Razordata has no equivalent of PG's `correlation` stat (physical ordering vs logical ordering) or extended statistics objects (functional dependencies, multivariate NDV, multivariate MCV lists).
- quote: "Type ColumnStats struct { DistinctCount int64; NullCount int64; MinValue []byte; MaxValue []byte; Histogram []HistogramBucket; RowCount int64; MostCommonVals [][]byte; MostCommonFreqs []float64 }"
- url: (internal source: internal/ENG/LS/stats.go)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [6] Razordata's plan memoization (xxhash, LRU 4096, schema-version invalidation) is unique among the three — neither SQLite nor PostgreSQL has equivalent full-plan memoization.
- Razordata uses xxhash (16 hex chars) to fingerprint AST → plan, stored in an LRU cache (4096 entries, REQ000584). Schema version bumps (DDL) invalidate all cached plans via key mismatch. SQLite has no plan memoization at all (prepared statements are re-planned). PostgreSQL's Memoize node (enable_memoize) only caches parameterized nested-loop-join scan results, not full plans. PG's prepared statement plan cache is separate and uses generic vs custom plan selection, not AST fingerprinting.
- quote: "TestSerializeKey_NotSHA256Length verifies the key is the 16-hex-character xxhash digest, not the 64-hex-character SHA-256 digest."
- url: (internal source: internal/SQF/PL/memo_test.go)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [7] Razordata's ANALYZE uses fixed 10K reservoir sampling with 256-bucket histograms; PostgreSQL's ANALYZE is configurable via default_statistics_target (default 100) per-column.
- Razordata's `analyzeTable` uses a fixed `sampleSize = 10000` for reservoir sampling and builds 256-bucket equi-depth histograms. SQLite's ANALYZE collects sqlite_stat1 (per-index NDV) and optionally sqlite_stat3/stat4 (histograms). PostgreSQL's ANALYZE collects up to `default_statistics_target` (default 100) entries per column for MCV and histogram arrays, configurable per-column via `ALTER TABLE SET STATISTICS`. Razordata's fixed sample size means it cannot trade off analysis time for accuracy on high-cardinality columns.
- quote: "const sampleSize = 10000"
- url: (internal source: internal/SQB/UT/analyze.go)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [8] Razordata already supports three join algorithms (HashJoin, MergeJoin, NestedLoopJoin) plus bushy tree grouping — exceeding SQLite's single nested-loop approach but missing PostgreSQL's parallel join variants.
- Razordata implements HashJoin (REQ000794), MergeJoin (REQ001102), NestedLoopJoin, HashCrossJoin, and BitmapHeapScan. SQLite only uses nested loops for joins. PostgreSQL supports NLJ, Hash, Merge, plus parallel hash joins, parallel merge joins, and incremental sorts. Razordata's `groupBushyJoins` (REQ000821) detects independent equi-join pairs for bushy execution — a capability neither SQLite nor PostgreSQL has at the plan-generator level (PG relies on the executor for bushy plans).
- quote: "groupBushyJoins detects independent equi-join pairs in the join order and groups them for bushy plan execution."
- url: (internal source: internal/SQB/EX/join_order.go)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [9] Razordata's razor_stat1 system table makes statistics queryable via SQL — a capability SQLite has (sqlite_stat1 is a regular table) but PostgreSQL exposes only through the pg_stats view.
- Razordata persists column stats to `razor_stat1` (REQ001317) with columns tbl, col_name, ndv, rowcount, null_count, min_val, max_val. This is queryable via `SELECT * FROM razor_stat1`. SQLite's `sqlite_stat1` is similarly a regular table. PostgreSQL's `pg_statistic` is a system catalog (superuser-only), with `pg_stats` as a readable view. Razordata's approach is well-aligned with SQLite's and arguably more accessible than PG's.
- quote: "var stat1Cols = []string{"tbl", "col_name", "ndv", "rowcount", "null_count", "min_val", "max_val"}"
- url: (internal source: internal/SQB/UT/analyze.go)
- source_type: primary
- published: 2026-07-09
- confidence: high

### [10] Razordata lacks SQLite's skip-scan optimization and PostgreSQL's covering-index detection via correlation statistics.
- SQLite's skip-scan (optoverview.html#skipscan) allows index usage even when the leftmost column is not constrained, by skipping to distinct values. Razordata does not implement skip-scan. PostgreSQL uses `correlation` statistics to predict heap fetch sequentiality and can use covering indexes via `IndexOnlyScan`. Razordata has `IndexOnlyScan` (REQ001107) and `tryIndexOnlyScan` but lacks the correlation stat that PG uses to estimate I/O patterns.
- quote: "The only way that SQLite can know that there are many duplicates in the left-most columns of an index is if the ANALYZE command has been run on the database."
- url: https://www.sqlite.org/optoverview.html
- source_type: primary
- published: 2026-03-22
- confidence: high
