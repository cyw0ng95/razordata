# F1: Cascades optimization framework & Top-K plan enumeration — how to restructure the optimizer's plan search from bottom-up DP to top-down memo/task-stack with multi-plan enumeration, assessing feasibility in Razordata's Go codebase.

## Findings

### [1] Razordata's current N3 optimizer uses bottom-up DP with bounded heap enumeration (n3HeapMaxSize=24), not full Cascades-style memoization
- quote: "type partial struct { tablesSet map[string]bool; order []string; cost float64; rows float64 }" and "heap := make([]partial, 0, n3HeapMaxSize)" (n3HeapMaxSize = 24)
- url: /workspace/internal/SQB/EX/join_order.go
- source_type: primary (codebase)
- published: 2025-2026
- confidence: high

The current N3 join ordering (join_order.go:11) maintains a min-heap of partial plans, iteratively extending the cheapest plan at each step. This is a bounded bottom-up DP approach with pruning (n3PruneMultiplier = 2.0). It does NOT store a full memo of (group, expression) pairs like Cascades does. The planner (planner.go:45) maintains a separate xxhash-based plan cache (map[string]*plan, maxPlanCacheSize=1024) for AST-fingerprint memoization, but this caches complete plans keyed by statement hash, not sub-expression alternatives.

### [2] The Cascades framework (Graefe 1995) restructures optimization as a top-down search with a Memo data structure storing equivalence classes of logical expressions
- quote: "The Cascades optimizer is a cost-based, extensible query optimizer that searches for the best plan by transforming logical expressions into physical implementations. It uses a top-down, rule-driven approach with a memo that groups equivalent logical expressions."
- url: https://www.microsoft.com/en-us/research/publication/the-cascades-framework-for-query-optimization/
- source_type: primary (original paper by Goetz Graefe)
- published: 1995 (IEEE Data Engineering Bulletin)
- confidence: high

The Cascades framework (Graefe, 1995, IEEE Data Engineering Bulletin 18(3)) introduced three key concepts: (1) a Memo structure that groups logically equivalent expressions into equivalence classes, (2) a top-down, rule-driven search that fires transformation rules on each group, and (3) an exploration that lazily produces physical implementations from logical groups. This is the foundation for the Volcano/Cascades optimizer lineage used in SQL Server, CockroachDB, and other systems.

### [3] NeuSO (SIGMOD 2026) demonstrates a top-down greedy plan enumerator that reduces enumeration cost from O(N!) DP to O(N·H) for subgraph queries
- quote: "We design a top-down greedy plan enumeration algorithm that generates high-quality execution plans. This approach minimizes excessive substate exploration typical in dynamic programming."
- url: https://arxiv.org/html/2509.23775v1
- source_type: primary (peer-reviewed, SIGMOD 2026)
- published: September 2025
- confidence: high

NeuSO (Yang, Zou, Zhao, SIGMOD 2026, doi:10.1145/3769810) introduces a top-down plan enumerator based on a "minimum cost" metric (Def 5.4) that represents the cost of the best possible plan for each subquery. The enumerator greedily picks the cheapest next vertex at each step, avoiding the exponential state space of DP. Complexity: O(N·H) where N is the number of query vertices and H is the number of candidates per vertex. This is directly applicable to Razordata's N3 approach — the current N3 heap-based DP already maintains a bounded set of partial plans but could be restructured as a top-down greedy with memoized minimum costs.

### [4] Shanbhag & Sudarshan (VLDB 2014) show that transformation-based (Cascades-style) optimizers need different join enumeration strategies than bottom-up DP
- quote: "We study the problem of join enumeration in transformation-based query optimizers, where the search space is explored using transformation rules rather than dynamic programming."
- url: http://www.vldb.org/pvldb/vol7/p1243-shanbhag.pdf
- source_type: primary (peer-reviewed, VLDB 2014)
- published: 2014
- confidence: high

Shanbhag & Sudarshan (VLDB 2014, 11 citations) demonstrated that join enumeration in Cascades-style optimizers requires different strategies than traditional DP. Their key insight: in transformation-based optimizers, the memo structure naturally stores all equivalent plans, but the enumeration order matters for efficiency. They propose techniques to efficiently enumerate the top-K plans within the Cascades framework by controlling which transformation rules fire and when. This is directly relevant to Razordata: if the N3 heap is restructured into a Cascades Memo, the enumeration strategy must change from "extend cheapest partial plan" to "fire join commutativity/associativity rules on memo groups."

### [5] PostgreSQL's GEQO uses genetic algorithms for queries with >12 joins, demonstrating that no single enumeration strategy is optimal for all query sizes
- quote: "The normal PostgreSQL query optimizer performs a near-exhaustive search over the space of alternative strategies... This makes the ordinary PostgreSQL query optimizer inappropriate for queries that join a large number of tables."
- url: https://www.postgresql.org/docs/16/geqo-intro.html
- source_type: primary (official PostgreSQL documentation)
- published: 2023
- confidence: high

PostgreSQL's GEQO module (PostgreSQL docs, Chapter 62) activates for queries with >= geqo_threshold (default 12) joins, switching from System R-style DP to genetic algorithms. This demonstrates the practical reality: Cascades-style full enumeration is expensive for large join counts. For Razordata, which targets embedded use cases (likely <10 tables per query), a Cascades Memo with top-K enumeration is feasible, but a fallback to genetic/heuristic search should be considered for edge cases with many tables.

### [6] Razordata's current architecture has a clean separation between PL (planner memo) and EX (tree construction) that maps well to Cascades group/equivalence classes
- quote: "type Planner struct { memo *Memo; opts PlanOptions }" and "BuildTree func(stmt PS.Stmt) (cost float64, err error)"
- url: /workspace/internal/SQF/PL/pl.go
- source_type: primary (codebase)
- published: 2025-2026
- confidence: high

The PL package (pl.go) already owns a Memo that caches plans keyed by AST fingerprint (xxhash64-based). The BuildTree hook delegates tree construction to EX. This separation maps directly to the Cascades model: PL's Memo becomes the group store, and BuildTree becomes the exploration function that fires rules on groups. The current xxhash-based memoization provides the key generation infrastructure; what's missing is the equivalence-class grouping (multiple physical plans per logical expression) and the rule-driven exploration.

### [7] Razordata's exhaustiveJoinOrder (≤4 tables) and N3 (5+ tables) could be unified under a Cascades Memo with top-K enumeration
- quote: "func (p *Planner) exhaustiveJoinOrder(baseTable string, joinTables []joinTableInfo, predicates []PS.Expr) []string" and "func (p *Planner) n3JoinOrdering(baseTable string, joinTables []joinTableInfo, wherePredicates []PS.Expr, pushedPredicates map[string][]PS.Expr) ([]string, float64)"
- url: /workspace/internal/SQB/EX/join_order.go
- source_type: primary (codebase)
- published: 2025-2026
- confidence: high

Currently, Razordata uses two separate strategies: exhaustiveJoinOrder for ≤4 join tables (generating all permutations, ~24 max), and N3 for larger queries. Under a Cascades Memo, both could be unified: small queries would naturally explore all combinations via rule firing (commutativity, associativity), while large queries would use bounded exploration with the memo preventing redundant work. The top-K enumeration (keeping K=3-5 best plans per group) would handle cost estimation uncertainty without the current heuristic pruning.

### [8] Top-K enumeration in a Cascades framework requires maintaining K best plans per equivalence group, with complexity O(K·N²·H) for N tables
- quote: "Optimizing Join Enumeration in Transformation-based Query Optimizers" — Shanbhag & Sudarshan show that top-K enumeration within Cascades requires O(K) work per group expansion
- url: http://www.vldb.org/pvldb/vol7/p1243-shanbhag.pdf
- source_type: primary (peer-reviewed, VLDB 2014)
- published: 2014
- confidence: medium

For Razordata with typical query sizes (2-8 tables), K=3-5 best plans per group would be practical. The current n3HeapMaxSize=24 already maintains multiple partial plans. The key difference: in Cascades, the K best plans are stored per equivalence group (not per partial plan), so the memo grows as O(groups × K). For an 8-table query, this means ~256 groups × 5 plans = ~1280 entries — well within the current maxPlanCacheSize=1024 (which would need to be increased).

### [9] The xxhash plan memoization in Razordata already provides the key generation needed for Cascades groups, but needs to be extended to store (logical_plan, physical_plans[]) instead of (key, single_plan)
- quote: "type Plan struct { Cost float64; MemoKey string }" and "entries map[string]*list.Element"
- url: /workspace/internal/SQF/PL/memo.go
- source_type: primary (codebase)
- published: 2025-2026
- confidence: high

The current Memo (memo.go) stores a single Plan per key. For Cascades, the Memo would need to store a MemoGroup containing: (1) the logical expression, (2) a list of physical implementations with costs, (3) whether the group has been fully explored. The xxhash-based key generation (SerializeKeyWithSchema) provides stable fingerprinting; the memo structure just needs to evolve from flat cache to group store.

### [10] Razordata's N3 predicate cache (predCache map[string][]PS.Expr) already implements the sub-expression deduplication that Cascades achieves via Memo groups
- quote: "predCache := make(map[string][]PS.Expr, len(heap)*len(allTables))" and "cacheKey := n3PredCacheKey(pp.tablesSet, tbl)"
- url: /workspace/internal/SQB/EX/join_order.go
- source_type: primary (codebase)
- published: 2025-2026
- confidence: high

The N3 join ordering already caches predicate lookups per (joined-set, candidate) pair (join_order.go:140-154). This is a micro-optimization of the same principle that Cascades Memo provides at a larger scale: avoid recomputing properties for equivalent sub-expressions. In a Cascades restructuring, this local cache would be subsumed by the Memo's group structure, eliminating the need for the separate predCache.
