| REQ001645 | SQB/OP | **Generalize parallel hash join to support arbitrary probe-side batch producers.** Current `ParallelHashJoin` (`parallel_hashjoin.go`) requires the probe side to be a `BatchProducer` and the build side to be materializable. It spawns N workers via `WorkerPool` to probe the hash table in parallel. This works for simple cases but doesn't support: (1) Nested loop join parallelization, (2) Merge join parallelization, (3) Adaptive worker count based on data size. **Fix:** (1) Extract a `ParallelProbe` utility in `SQB/UT/parallel.go` that takes a hash table, a probe batch producer, and a worker count. (2) Re-implement `ParallelHashJoin` using `ParallelProbe`. (3) Add a `Parallelism` parameter to `VectorizedHashJoin` that can be set by the planner when the build side is large (> 10K rows). (4) Add `BenchmarkParallelHashJoin_LargeBuild` that measures speedup on a 100K-row build side. Estimate: ~150 lines, 3 files, 1 day. | low | medium | REQ001587, REQ001622 | SQB/OP/parallel_hashjoin.go, SQB/UT/parallel.go, SQB/OP/op_vec_join.go |
| REQ001653 | ENG/LS | **SST block column stats: per-column min/max during block construction.** SST blocks currently have no per-column statistics. Range scans like `WHERE x > 10` must decode every row in every block. **Fix:** (1) In `sstWriter`, as each row key-value is appended to a block, decode the value and track per-column min/max for each column in the schema. (2) Store the column stats as a compact trailer appended to each block: `[colIdx:min:max]...` using varint encoding. (3) In `sstReader`, during block open, parse the column stats trailer and expose them via a `BlockColumnStats(colIdx) (min, max any, ok bool)` method. (4) The stats are scoped to a single block — they are not aggregated across blocks (that's REQ001655). (5) Add `TestSSTBlock_ColumnStats` verifying min/max correctness for int, float, and text columns. Estimate: ~80 lines, 2 files, 0.5 day. | high | small | none | ENG/LS/sst_writer.go, ENG/LS/sst_reader.go |
| REQ001656 | SQB/EX | **Cross join with unaliased table references produces too few rows.** SLT corpus `random/select/slt_good_124` has 168 failures (out of 4790) where cross-join queries return fewer rows than expected. All affected queries have unaliased table references in the FROM clause (e.g., `FROM tab0, tab1 AS cor0`). (2) Fix the row-count discrepancy so that `tab0` (3 rows) × `tab1` (3 rows) = 9 rows, not 3. (3) Verify fix against all 168 failing cases in `slt_good_124`.
