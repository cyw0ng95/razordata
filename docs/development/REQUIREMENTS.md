| REQ000842 | EX/op | **EXCEPT/INTERSECT fully materializes both sides before computing result — O(2N) memory for set operations.** `CompoundOp.Next()` (`compound.go:102-113`) always calls `drainAll(ctx, c.left)` and `drainAll(ctx, c.right)` for EXCEPT/INTERSECT/UNION (non-UNION-ALL). For a mixed-mode 8-branch compound (4 EXCEPT/INTERSECT ops at different tree levels), each intermediate materialization duplicates rows that are then deduped again by the parent operator. In the SLT test's worst-case 8-branch compound with 100-row tables, this quadruples memory: 100 rows scanned → 100 materialized → 100 merged → 100 deduped → repeat at next tree level. EXCEPT and INTERSECT only need a hash set of the right side's distinct keys to probe against, not the full right-side row data. **Fix:** (1) For `CompoundExcept`: drain right side first, build `map[string]bool` of distinct keys, then stream left side and emit rows whose key is NOT in the right map. No left-side materialization needed. (2) For `CompoundIntersect`: drain right side first, build `map[string]bool` of distinct keys, then stream left side and emit rows whose key IS in the right map + track emitted keys. No left-side materialization needed. (3) Preserve the current materialized path as fallback when ORDER BY/LIMIT/OFFSET is present (since those require the full result set). (4) For UNION (dedup), still need both sides materialized for the dedup pass — but after dedup, the result can be streamed out if no ORDER BY/LIMIT. (5) Benchmark: `BenchmarkSelect4_Compound8` (mixed EXCEPT/UNION, 15 rows/branch) should see -40% memory (from 1.4KB to under 1KB) with no time regression. Worst-case 8-branch EXCEPT chain at 100 rows/branch should see -60% peak memory. | high | medium | — | EX/compound.go |
