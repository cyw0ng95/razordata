| REQ001645 | SQB/OP | **Generalize parallel hash join to support arbitrary probe-side batch producers.** Current `ParallelHashJoin` (`parallel_hashjoin.go`) requires the probe side to be a `BatchProducer` and the build side to be materializable. It spawns N workers via `WorkerPool` to probe the hash table in parallel. This works for simple cases but doesn't support: (1) Nested loop join parallelization, (2) Merge join parallelization, (3) Adaptive worker count based on data size. **Fix:** (1) Extract a `ParallelProbe` utility in `SQB/UT/parallel.go` that takes a hash table, a probe batch producer, and a worker count. (2) Re-implement `ParallelHashJoin` using `ParallelProbe`. (3) Add a `Parallelism` parameter to `VectorizedHashJoin` that can be set by the planner when the build side is large (> 10K rows). (4) Add `BenchmarkParallelHashJoin_LargeBuild` that measures speedup on a 100K-row build side. Estimate: ~150 lines, 3 files, 1 day. | low | medium | REQ001587, REQ001622 | SQB/OP/parallel_hashjoin.go, SQB/UT/parallel.go, SQB/OP/op_vec_join.go |
| REQ001646 | SQB/AG + SQB/EX | **Vectorize window function execution (ROW_NUMBER, RANK, LAG, LEAD, etc.).** `WindowOperator` in `AG/window.go` executes window functions row-by-row. It is not in `vec_transform.go`, so window function queries never benefit from vectorized execution. For queries like `SELECT ROW_NUMBER() OVER (PARTITION BY x ORDER BY y) FROM t`, the window function is evaluated per row, and the Sort/Project/Scan operators above/below it also fall back to row mode. **Fix:** (1) Create `VectorizedWindowOperator` that implements `BatchProducer` and processes batches of rows through the window function pipeline. (2) Add `transformWindowOperator` to `vec_transform.go` that converts `WindowOperator` to `VectorizedWindowOperator`. (3) For ROW_NUMBER and RANK, use a batch-parallel algorithm (partition → sort within partition → assign numbers). (4) For LAG/LEAD, use a sliding window over the batch. (5) Add `TestWindowFunction_Vectorized` that verifies correctness against the row-based implementation. | REQ001647 | ENG/LS | **Make columnar SST block layout the default format.** Columnar SST (`columnar.go`, REQ000314) stores block data in column-major order (all values for column 0, then column 1, etc.) instead of row-major. This enables: (1) Column pruning during scan (only decode requested columns), (2) Better per-column compression (same-type values compress better), (3) Vectorized decoding (SIMD-friendly column strides). Currently row-major is the default; columnar is opt-in. **Fix:** (1) Set `layoutColumnar` as the default block layout in `SSTWriter`. (2) Update `SSTReader` to handle both layouts for backward compatibility during the transition period. (3) Add a migration path: on `Engine.Open`, rewrite SST files with the old layout to the new layout. (4) Benchmark `SELECT col1, col2 FROM t WHERE col3 > 10` to measure column pruning benefit.
