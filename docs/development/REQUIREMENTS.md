| REQ000832 | EX/eval | **Aggregate inside COALESCE/scalar function returns NULL instead of the aggregate value.** `SELECT COALESCE(NULL, MIN(ALL -30) * 45 * 77) FROM t` returns NULL but should return -103950. The CASE/COALESCE NULL semantics work correctly for non-aggregate arguments (e.g. `SELECT COALESCE(NULL, 99)` returns 99, `SELECT COALESCE(CASE WHEN NULL THEN 1 END, 99)` returns 99), but when the second argument to a scalar function is an aggregate, the aggregate is not evaluated. Partial fix: `containsAggregate` in `planner.go:1965` now recurses into `*PS.FunctionCall.Args`, but the resulting `splitSelectCols` still treats the whole `COALESCE(...)` as a single aggregate expression and never routes MIN through the Aggregate operator. **Fix:** (1) When splitting SELECT cols, recognise that scalar function args containing aggregates are *not* themselves aggregates — extract the inner aggregate and re-wrap the surrounding expression. (2) Add test: `TestCoalesceWithAggregate` verifying `SELECT COALESCE(NULL, MIN(x) * 10) FROM t` returns the aggregate value, not NULL. (3) Verify against oracle. | high | medium | iter-31 | EX/planner.go, EX/aggregate.go |
| REQ000847 | EX/exec | **LIMIT without ORDER BY still materializes the full result — many select4 queries have LIMIT but no ORDER and return only first few rows.** For example, queries like `SELECT ... FROM t1,t2,t3 WHERE ... LIMIT 10` should stop scanning after 10 matches are found. Currently, the entire join result is materialized before LIMIT can apply. With 100-row tables and a 5-table join producing 10¹⁰ rows, even finding 10 matches requires the full materialization. This is independent of predicate pushdown (REQ000843): even with optimal pushdown, some queries still need scanning to find the LIMIT count. **Fix:** (1) Make `Limit.Next()` short-circuit when the count is reached, returning `ErrNoRows` immediately. (2) Push LIMIT down into NLJ: when the inner scan has produced enough rows matching the join predicate, stop pulling from the inner side. (3) Track `limitRemaining` in NLJ: decrement per output row, return `ErrNoRows` when it hits 0. (4) Apply similar optimization to Filter chains: when Limit is below Filter, the Filter can stop evaluating once the limit is reached. (5) Verify: select4 queries with LIMIT 10 over 5-table joins should complete in milliseconds, not seconds. | medium | small | — | EX/intermediate.go, EX/nlj.go |
