## 3. REQ001125 — CHANGES() and TOTAL_CHANGES() return 0

### Diagnosis (read `eval.go`)

The function `evalChanges` (or equivalent) reads a per-connection counter
that the in-memory write path doesn't bump. The counter probably exists
for the LSM path but not for the in-memory writer.

### Fix strategy

1. Locate the eval path for `CHANGES()` / `TOTAL_CHANGES()`.
2. Trace the in-memory writer (`writers.go`) to see where the
   insert/update/delete counter lives.
3. Add a counter bump in the in-memory path, OR re-route the eval to
   read from a unified counter.

### Regression test

- INSERT 1 row.
- Verify `SELECT CHANGES()` returns 1.
- INSERT another row.

## 4. REQ001127 — NULL NOT IN (list)

### Diagnosis

The case's Want is `[[nil]]` (1 row of NULL) but the **oracle** (modernc
sqlite) actually returns `[]` (0 rows). The diff is razor vs oracle, and
oracle says `[]` while the case's `Want` says `[[nil]]` — that's a **case
data inconsistency** in the corpus.

Per SQL standard: `NULL NOT IN (10, 20)` is NULL (three-valued logic), so
the WHERE filter rejects the row (only TRUE rows survive). Modernc is
correct, the case Want is wrong.

### Fix strategy

**Option A: Fix the case** (correct the Want to `[][]any{}`).
**Option B: Fix the evaluator** (match the case Want, which is wrong).

The dual runner diffs razor vs oracle, not razor vs Want. Since oracle
returns `[]`, **razor returning `[]` is correct** — and the case as
written would still fail. So Option A is the right fix: update the case
Want to `[][]any{}` to match modernc.

### Regression test

`TestNotIn_NullThreeValuedLogic` in `internal/SQB/EX/req001127_test.go`:
- `SELECT NULL NOT IN (1)` → NULL.
- `SELECT 5 NOT IN (1, NULL)` → NULL.
- `SELECT 1 NOT IN (1, NULL)` → FALSE.
- `SELECT v FROM t WHERE v NOT IN (10, 20)` with NULL `v` → 0 rows.

## 5. REQ001128 — UNION NULL handling

### Diagnosis

Razor returns `[[<nil>] [<nil>] [2]]` for `union_all_with_nulls` (3 rows
total) where the expected is 4 rows `[1, 1, 2, 2]`. The column values are
swapped or NULLs are being treated as 1s, and 1 row is missing.

The case setup is:
```sql
CREATE TABLE a (x INTEGER PRIMARY KEY);
INSERT INTO a VALUES (1), (NULL);
CREATE TABLE b (x INTEGER PRIMARY KEY);
INSERT INTO b VALUES (NULL), (2);
SELECT x FROM a UNION ALL SELECT x FROM b ORDER BY x;
```

So a has 2 rows: 1, NULL. b has 2 rows: NULL, 2. UNION ALL → 4 rows:
1, NULL, NULL, 2 (sorted: NULL, NULL, 1, 2).

Razor's got: `[[<nil>] [<nil>] [2]]` (3 rows: NULL, NULL, 2). **The `1`
is missing AND it's been replaced with another NULL.** Plus one row
missing.

**Most likely root cause:** the UNION ALL output column reader maps to
the wrong source column, picking NULLs from column index 0 (which
should hold the `x` value) and missing the `1`.

**Alternative:** the ORDER BY treats NULL as 0 or some other sort key
that drops a row.

### Fix strategy

1. Read `compound.go` UNION ALL path.
2. Trace the output column resolution when one of the inputs has
   NULLs.
3. Compare to the UNION DISTINCT path that has the same issue.
4. Add a minimal 2-table UNION ALL test with one NULL row.

### Regression test

`TestUnion_AllWithNulls` in `internal/SQB/EX/req001128_test.go`:
- `SELECT 1 UNION ALL SELECT NULL` → 2 rows: 1, NULL (sorted).
- `SELECT x FROM a UNION ALL SELECT x FROM b` with a={1,NULL}, b={NULL,2}
  → 4 rows.

## 6. REQ001129 — INSERT ... SELECT returns 0 rows

### Diagnosis

`INSERT INTO dst SELECT * FROM src WHERE v > 15` returns 0 rows in dst.
The setup seeds src with 2 rows `(1,10), (2,20)`. The expected result is
`[[20]]` (1 row with v=20).

The most likely root cause: `buildInsertRow` for the INSERT...SELECT path
doesn't iterate the SELECT subquery, OR the column mapping is wrong (src
has 2 columns, dst has 2 columns, should be 1:1).

### Fix strategy

1. Read `writers.go` `buildInsertRow` for the INSERT...SELECT branch.
2. Read the source.go INSERT...SELECT source reading path.
3. Add a minimal test that does an INSERT...SELECT with simple data
   and verify the rows land in the target.

### Regression test

`TestInsertSelect_ColumnMapping` in `internal/SQB/EX/req001129_test.go`:
- Create src(1 row), dst(empty).
- `INSERT INTO dst SELECT * FROM src`.
- Verify `SELECT count(*) FROM dst` returns 1.

## 10. Outcome (2026-07-01)

### What shipped

| REQ | Commit | What |
|---|---|---|
| REQ001125 | `9cd471f` | Fix `CHANGES()`/`TOTAL_CHANGES()` returning 0 in driver path. Root cause: `razor/driver/conn.go` ExecContext used `Prepare+Stmt.Exec` which bypassed `SE.Session.Exec` where per-session counters are maintained. Fix: route through `c.session.Exec()`. Also added session-counter-accessor fallback to `evalChangesNative`/`evalTotalChangesNative` in `function_registry.go`, matching existing `evalLastInsertRowIDNative` pattern. |
| REQ001126 | (pre-fixed) | `correlated_subquery_exists` and `correlated_subquery_not_exists` already pass — closed as pre-fixed by REQ001098. No code change. |
| REQ001127 | (in iter commit) | Fix `NOT IN` with NULL values. Root cause: `compileFilterExpr` compiled `NOT (InExpr)` path, where `compileInExpr` returned `false` (not found in map) for NULL column values, which negation turned into `true` → row passed when it should have been filtered out. Fix: skip compiled path for `NOT InExpr` — the per-row Eval path handles three-valued logic correctly. |
| REQ001128 | (in iter commit) | Fix `UNION ALL`/`UNION DISTINCT` with NULL PKs. Two bugs: (1) `ExtractPK` in `storage.go` generated synthetic rowid `1` for first NULL PK, colliding with user-assigned PK `1`. Fix: track max PK value via `NextRowID` so generated IDs are always `max_pk + 1`. (2) NULL PK columns were stored as NULL instead of auto-generated value. Fix: in the store INSERT path, after `ExtractPK` generates a synthetic ID, update the row data to store the generated ID instead of NULL (matching SQLite INTEGER PRIMARY KEY behavior). |
| REQ001129 | (in iter commit) | Fix `INSERT INTO dst SELECT * FROM src` with store-backed tables. Two bugs: (1) `buildWriterOp` in `ex.go:1428` always used `NewInsert` (no store) for INSERT...SELECT even when `e.store != nil`. Fix: use `NewInsertWithStore` when store is available. (2) `nextFromSelect` in `writers.go` only appended rows to in-memory table slice, never wrote to the store engine. Fix: added store-backed INSERT path in `nextFromSelect` mirroring the standard INSERT store path. |
