# REQ001113/1155/1156 — Cross-join Cardinality & Join-Elimination Bugs

> **Status**: in progress (2026-07-01). Combines three related join-planner
> bugs surfaced during select4.test / select5.test regression work.

## 1. Background

Three REQs in `REQUIREMENTS.md` describe symptoms of the same family of bugs
in the join planner:

- **REQ001113** (high, large) — `select4.test` shows 330/3857 records failing
  with both under-count and over-count cardinalities for implicit
  comma-joins with equality predicates. Different table orderings of the
  same query produce different (wrong) cardinalities.
- **REQ001155** (high, small) — Join elimination (`collectReferencedTables`
  in `internal/SQB/EX/planner.go:1678`) drops joins whose columns are
  referenced **only** in the `JOIN ON` clause.
- **REQ001156** (medium, medium) — `groupBushyJoins` heuristic splits
  non-independent groups, breaking select5 chain-equi-joins.

### Important note on REQ001156

The fix for REQ001156 was already shipped in commit `e00d132` (Wed Jul 1
00:49:57 2026) under the commit message "fix: REQ001113". That commit
actually contains three related bushy-join bugfixes:

1. `extractTableColumn` resolves bare Ident columns via SLT naming
   convention (e.g. `d6` -> `t6.d`) so `groupBushyJoins` can detect
   cross-table equi-join dependencies.
2. `groupBushyJoins` transitive dependency: tables connected through a
   shared equi-join table are no longer incorrectly split.
3. `groupBushyJoins targetGroup`: dependent tables are appended to the
   correct group, not always the last one.

select4.test failures dropped from 59 -> 25 (58% reduction) as a result.

REQ001156 is essentially **shipped in spirit** (the heuristic bug is
fixed), but the REQ row in TBD was never deleted and the original REQ

## 2. REQ001155 — Join elimination drops ON-only joins

### Diagnosis (read of `planner.go:1678-1724`)

```go
// REQ001076: do NOT walk JOIN ON clauses — tables that appear only in
// join conditions can be eliminated when not referenced in SELECT/WHERE
// /ORDER BY/GROUP BY/HAVING. The join condition is only meaningful when
// both sides contribute columns to the output.
```

This comment captures the original intent: when a table's columns are
**never** referenced anywhere except the join condition, the table can be
eliminated *only if* the join condition itself becomes trivially true
(meaningful when "both sides contribute columns to the output"). The
current code does not check that — it just drops the join unconditionally
when `refTables[j.Right]` is false.

For `SELECT t1.a FROM t1 JOIN t2 ON t1.id = t2.t1id`:
- `t2.t1id` only appears in the ON clause.
- `refTables` = `{t1: true}`.
- The `s.Joins` filter at line 2093-2102 drops the t2 join.
- Result: wrong output (the t1 scan runs without the t2 join, but the
  query's meaning is "give me t1.a rows where t1.id has a corresponding
  t2.t1id").

### Fix strategy

The join elimination's safety condition must be: **a join can be
dropped only if neither side's columns appear in the projection/wher/
order/group/having/ON**. The ON clause is part of the query's semantic
contract — it constrains which rows survive the join.

Two viable fixes (REQ001155 lists both):
1. Include JOIN ON clauses in `collectReferencedTables` — but this
   breaks the existing REQ001076 join elimination optimization for the
   case where ON columns aren't otherwise referenced.
2. Special-case the join elimination: never drop a join whose ON clause
   references the joined table. This preserves REQ001076's optimization
   for the "ON-only, but the predicate is tautological" case (e.g.,
   `JOIN t2 ON 1=1`) while fixing the real bug.

**Approach: option 2.** It is the smaller, more targeted change.

Implementation:
- In the `s.Joins` filter loop (line 2093-2102), before dropping a join
  whose `j.Right` is not in `refTables`, check whether `j.On` references
  `j.Right` (or `j.RightAlias`). If yes, keep the join.
- The check reuses `collectTablesFromExpr` (line 1729) on the ON clause.

### Regression test

`TestJoinElimination_PreservesONReferencedTable` in
`internal/SQB/EX/req001155_test.go`:

- Seed `t1` and `t2` in DT.
- Parse and plan `SELECT t1.a FROM t1 JOIN t2 ON t1.id = t2.t1id`.
- Verify `s.Joins` is not empty (join is preserved).
- Execute the query and verify the output row count matches the seed
  data (e.g., 2 rows from t1, 1 row in t2 -> 1 matching row).

## 3. REQ001113 — Remaining sub-items after `e00d132`

`e00d132` fixed the `groupBushyJoins` (REQ001156) sub-item. Three remain:

### 3.1 `splitPredicatesByTable` mis-routes predicates for implicit comma-joins

`planner.go:1236` — when a predicate like `a3=b9` is split per table,
both sides mention two tables. The current implementation may assign it
to only one table or to neither. Need to add a test that verifies a
2-table implicit comma-join with `t1.x = t2.y` puts the predicate in
**both** tables' per-table maps (or in the cross-table return slot).

**REPRO:** `SELECT x1, d9 FROM t1, t9 WHERE 281=a1 AND c9=232` — the
two predicates should both be pushed to single-table filters (not lost
or duplicated). Under-count to 1 row from 3 indicates one predicate is
being dropped or the cross-table predicate is not being applied.

### 3.2 `eliminateCommonSubexpressions` may dedup simple equality predicates

`planner.go:3077` — CSE on simple equalities `a=1 AND b=2` could collapse
to `a=1 AND a=1` if the expression fingerprinting is too aggressive.
Verify it preserves distinct constant references per table.

**REPRO:** `SELECT x1, d9 FROM t1, t9 WHERE 281=a1 AND c9=232` — got 1
row, want 3. If CSE collapsed both, the remaining predicate would be
single-sided and over-filter.

### 3.3 HashJoin/NLJ order-dependent cardinality

The remaining 25 select4 failures after `e00d132` may be due to the
HashJoin or NLJ operators producing different cardinalities for
different orderings of the same join. Need to:

- Add cardinality assertion to `HashJoin.buildAndProbe` for known
  test cases.
- Add cardinality assertion to `NestedLoopJoin.Next`.
- Add `TestCrossJoin_Cardinality_AllPermutations` running 5
  representative failing queries with all table orderings, verifying
  identical cardinality.
